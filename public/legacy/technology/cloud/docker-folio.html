The whole story first

Keep this picture in your head. Every chapter fills in one part of it.

The one ideaA container is an ordinary Linux process that has been given a private view of the system, a limit on what it can use, and its own set of files. Everything else is tooling around that one fact.

Added explanation

Read the picture from top to bottom.

You write a Dockerfile (a text recipe for building an image). You run a build, and out comes an image (a sealed package of files and settings). You push the image to a registry (a storage service for images). Any host (the machine that runs your software) can pull it. The host then starts a container (a running process made from an image).

Three Linux kernel features do the real work at the bottom of the picture. Docker did not invent them. Docker made them easy to use. The kernel (the core of the operating system, which controls hardware and processes) is the star of this book, even though it is hidden.

The demo application. The course builds one small three-tier web application (an app split into a front end, a back end and a database) and carries it from a laptop to the cloud. It has a React front end (the part users see), two nearly identical APIs (the parts other programs call), one in Node.js and one in Go, and a PostgreSQL database. Each part is deliberately tiny. The networking and the handling of passwords are deliberately realistic.

The two problems containers solve

Software that works here should work there. Containers turn that wish into a package.

The one ideaContainers do not make software simpler. They move the messy setup steps out of human hands and into one package that behaves the same everywhere.

The problem: "it works on my machine"

From the course

The course opens with a familiar joke. You build an application and it runs well on your laptop. Then something goes wrong when you move it to production (the real system that real users depend on). The joke's answer is to ship your laptop. Docker does something close to that. It makes your local environment as close as possible to the production environment.

The course names two stages of the software development life cycle (all the stages of making and running software) where this pain lives.

Development. You join a company and receive a laptop. You install many tools, run scripts and configure things by hand. It is long, complex and full of chances for human error. It is harder still when a team mixes Windows, Mac and Linux. With Docker, setup becomes one command, docker compose up, and a new person can be working within their first hour.

Deployment. To run your app on a server, you first create an Ubuntu server (Ubuntu is a popular version of Linux). Then you run configuration software such as Ansible (a tool that sets up servers by script) to install dependencies (other software your app needs in order to run). You copy your code across and start it with the right options. There are many steps, and it is hard to get them right every time.

What the package changes

From the course

Containers bring a single standard package. As long as a server has a container runtime (a program that can start containers), you take the standard container image and run it with specific options. Docker provides one runtime, and there are others. You stop worrying about the operating system and dependencies underneath, and you get repeatable, reliable results.

Added explanation

Why were the old steps fragile? Each step changes a machine that already has a history. Two servers built a month apart get different package versions. Someone fixes one server by hand and forgets to tell anyone. Experts call this configuration drift (machines slowly becoming different from each other).

An image attacks this at its source. You do not repair a running machine. You build a new sealed package and replace the old one. If it worked in testing, the very same bytes go to production, so there is nothing left to drift.

One limit is worth keeping in mind. The image fixes the files. It does not fix the kernel, the CPU type, the network or the data. A container can still behave differently on another host for those reasons. You will meet each of them later.

Hypothetical scenario

Bazaar Box: the first week

Workload. A web shop built from a Python service, a Node.js service and a PostgreSQL database.

Constraints. Twelve developers on three operating systems. New hires need three days to get running. Releases are done by hand on Friday nights.

What happened. A release failed because the server had a newer library than the laptops. The fix took four hours during a sale.

Decision. The team agrees on one rule: the thing that was tested must be the thing that ships. They choose container images as the unit of release.

Trade-offs. They gain repeatable releases and faster joining. They pay with new things to learn, a registry to run, and a slower first build. Images also do not solve the data problem, because the database still needs careful care. Chapter 9 returns to that.

Check yourself

ExplainIn one sentence, what moved when the team adopted containers?

The setup steps moved from people working on machines into an image build that a computer repeats exactly.

PredictThe same image runs on two hosts. One host has a much older Linux kernel. Can they behave differently?

Yes. The image carries files but not a kernel. An app that needs a newer kernel feature can fail on the older host.

ChallengeSomeone says: "Containers just hide complexity." How do you answer?

They are partly right. The complexity still exists, but it now lives in one reviewed, versioned file that a machine repeats. Hidden in a recipe is far better than hidden in someone's memory.

Image and container, and the standard behind them

The most important pair of words in this book, and the three specifications that make them portable.

The one ideaAn image is a thing you store. A container is a thing you run. Confusing the two causes most beginner mistakes.

What is an image?

From the course

Docker's website calls a container image a lightweight, standalone, executable package of software that includes everything needed to run an application. Think of a box. Inside are the operating system dependencies, the runtime, your libraries and your code. For a Python app that means the right Python version, libraries such as SQLAlchemy and FastAPI, and your own code, all bundled together.

The beauty is the standard interface. If you need two copies of an application, you run the image twice. You need three, you run it three times.

The course draws a sharp line. A container image is the artefact that has all the dependencies inside it. A container is what you run from that image. In object-oriented programming (a style where you define a class, then create objects from it), the image is like a class and the container is like an instance of that class. Every copy starts the same.

Added explanation

Three facts follow from this, and each one will return.

The image never changes when you run it. Containers cannot edit their image. Anything a container writes goes into a thin extra layer (one saved set of file changes) that belongs to that container alone (Chapter 6).

Containers are cheap to throw away. Since the image is safe and unchanged, you can delete a container and start a fresh one in moments. That is why good container design keeps nothing important inside the container (Chapter 9).

A container is not a small computer. It does not boot. When it starts, one process starts. When that process ends, the container stops (Chapter 17).

Lab: two containers, one image, no shared state$ docker run --name one lab/base sh -c 'echo x > /newfile'$ docker diff oneA /newfile$ docker run --rm lab/base ls /newfilels: cannot access '/newfile': No such file or directoryThe first container's change never touched the image.

The standard: OCI

From the course

Early on, several companies built slightly different versions of the same idea. They realised one shared standard made more sense. That is the Open Container Initiative, or OCI (a group that writes open standards for containers). Docker, Google, VMware, Microsoft, Dell, IBM, Oracle and others came together to define what a container is and how it should run.

The OCI defines three specifications:

  • The image specification says what an image must contain: its metadata and its format, which is a file system that can be stored and moved.
  • The runtime specification says how to take such an image and run it as a container.
  • The distribution specification says how images are shared, which means registries and pushing and pulling.

When the course says "Docker image", it means Docker's implementation of this standard. If Docker is the only tool you use, this may not matter much. It matters when you meet other tools, because the format is shared.

Added explanation

A standard is a promise that lets strangers work together. You can build with Docker and store in GitHub's registry. You can then run on Kubernetes (a system for running containers across many machines) with a different runtime. Each step only depends on the standard. Chapter 24 calls this portability, and it is why there are so many ways to run a container. At the time of checking, the version files in their repositories showed image 1.1.1, distribution 1.1.1 and runtime 1.3.0.

Hypothetical scenario

Meridian Group: three tools, one format

Workload. A large insurer with 300 developers and several business units.

Constraints. One unit uses Docker Desktop. Another must avoid its licence cost and uses Podman. Production runs on Kubernetes with containerd.

Decision. The platform team writes one rule: every team must publish an OCI image to the central registry. They do not care which tool built it.

Trade-offs. Teams keep their freedom and the platform stays simple. The cost is that small differences between tools can still surprise people, such as default users or build features. So the team runs one shared test on every image before release.

Check yourself

ExplainWhy is "class and instance" a good picture, and where does it break?

It shows one definition and many running copies. It breaks because an image is a stored set of files, not code you call, and because each container also has its own writable layer (where its changes go).

DiagnoseA teammate installs a tool inside a running container, restarts from the image the next day, and the tool has gone. Why?

They changed the container, not the image. A new container starts from the unchanged image. The fix is to add the tool to the Dockerfile.

Challenge"Why should I care about OCI if I only use Docker?"

Because it is why your images will run on nearly every platform you might later choose, without being rebuilt. It protects your future options.

From bare metal to containers

Each step in this history solved the last step's pain and created a new trade-off.

The one ideaThe difference between a virtual machine and a container is one thing: who owns the kernel. Size, speed and isolation all follow from that.

Bare metal

From the course

Before virtual machines (software computers), there were just computers. Today we call this bare metal (running directly on the hardware). You have a physical server, an operating system, some binaries and libraries, and your applications installed on top. Your laptop works this way too.

The course lists the pains:

  • Dependency hell. Applications share one layer of libraries. If they need different versions, you must change the app or carve up the system with tricks such as different PATH settings per process.
  • Low utilisation. Because of those conflicts, you put fewer apps on each server. If each app uses one CPU core and your server has 64, most of it sits idle.
  • Large blast radius (how much else breaks when one thing breaks). A problem in one app can directly hurt another app on the same host, so every change feels dangerous.
  • Slow start and stop. A physical server takes minutes to reboot, which hurts uptime.
  • Very slow provisioning (preparing a new machine for use). In your own data centre, buying, installing and wiring hardware takes days or weeks. With a co-location or bare-metal provider it takes hours.

Virtual machines

From the course

Those pains led to virtual machines, or VMs (software computers that run inside a real one). The physical server stays, and now a hypervisor (software, helped by hardware, that splits one computer into several) sits on it. It carves CPU cores, memory, storage and devices into smaller isolated pools. Each pool looks like its own hardware, so you can install an operating system, libraries and your app on it. Each app gets its own isolated machine.

There are two types. A type 1 hypervisor runs directly on the hardware with no operating system below it, so it loses less performance. AWS Nitro is one example, used to create virtual machines on Amazon's servers. VMware vSphere is another. A type 2 hypervisor runs on top of a normal operating system. You would use one such as VirtualBox on a laptop.

VMs improve things a lot. Each has its own libraries, so dependency hell ends. Servers can be split into many small chunks, so utilisation rises. This is what lets a cloud provider offer you many machine types: they own big machines and sell you slivers. Failures in one VM should stay in that VM, so changes are safer. Start and stop still take minutes, but less than a physical server. New VMs appear within minutes, and you can stop paying within minutes too.

Correction

Two small fixes

The course names vSphere as the type 1 hypervisor. To be exact, ESXi is the hypervisor inside the wider vSphere product. Also, the line between types is softer than it sounds. KVM (a hypervisor built into Linux) turns a normal operating system into a hypervisor, so it does not fit either box neatly.

Containers

From the course

Containers go further. The host can be a physical machine or a virtual machine. Above the operating system sits the container runtime, a piece of software that knows how to take an image and run it. It plays a role similar to the hypervisor.

Here is the key difference. A virtual machine runs its own copy of the kernel. Linux containers share the kernel with the host. Isolation comes from kernel features instead, which the next chapters explain. You do not get quite the same isolation as a VM, but you get quite good isolation if you configure things properly. Each container still has its own binaries and libraries.

This course covers Linux containers only. Windows containers exist, and they are a separate topic.

The course sorts the software into two groups. Desktop container platforms such as Docker and Podman are complete tools for the whole life cycle: images, containers, networking. Container runtimes such as containerd and CRI-O are narrower. They take a compliant image and run it.

Compare the old pains again. There are no dependency conflicts. Utilisation is better still, because a VM image is usually gigabytes while a container image is usually megabytes. (Multi-gigabyte container images exist, but they are not ideal.) Blast radius is small, though isolation is weaker than a VM's. Start and stop take seconds, and creating a container is about the same as starting one. Finally, containers are light enough to use during development, so development and production can match closely. That removes a whole class of small, puzzling bugs.

Stacking them together

From the course

A host can be a VM, so we can get a little "Inception" about it: a physical server runs VMs, and each VM runs containers. The course says this is what most people working with containers in the cloud are doing. It combines the safety and easy management of VMs with the speed and efficiency of containers.

The real challenge then becomes managing all those containers across machines. That is the job of an orchestrator (software that decides where containers run and keeps them running), such as Kubernetes, HashiCorp Nomad or Docker Swarm. A node is one machine in such a system.

Hypothetical scenario

Ledgerline: mixing the three layers

Workload. A payments firm runs a card-processing service and a low-risk public website.

Constraints. Card data rules demand strong separation. One fraud model needs a specific hardware accelerator.

Architecture. The website runs in containers on shared VMs. Card processing runs in containers too, but on its own dedicated VMs. The fraud model runs on bare metal, since no hypervisor passes through that device well.

Failure behaviour. A bug in the website is limited to its VM group, so an attacker who escapes a container still faces a hypervisor wall before reaching card data.

Trade-offs. Three layers mean three things to patch and monitor. They pay that price where the risk is high and keep things simple where it is low. This is the judgement to copy: choose by risk, not by fashion.

Check yourself

PredictYou start 50 small containers and 50 small VMs on the same server. Which group uses less memory, and why?

The containers. Each VM runs a full kernel and operating system. The containers share one kernel, so they carry only their own process memory.

DiagnoseA Linux container runs fine, but a Windows program inside it fails at once. Why?

Linux containers share a Linux kernel. A Windows program expects the Windows kernel, and an image cannot bring its own kernel.

Challenge"Containers are just lightweight VMs." How do you reply?

They feel similar from the outside, but they differ at the base. A VM has its own kernel and virtual hardware. A container is a process on a shared kernel. That is why it starts in seconds, and it is why a kernel bug can affect every container on the host.

Namespaces: what a process can see

The first of three kernel features. It builds the walls by editing what a process is allowed to know.

The one ideaA namespace does not move a process anywhere. It changes the answer the kernel gives when the process asks, "What exists?"

The problem

Added explanation

On a normal Linux machine, every process lives in one shared world. It can list all processes, see all network ports (numbered doors for traffic) and see every user. So two web servers both wanting port 80 will clash, and a process can inspect its neighbours. To run many apps safely on one kernel, each one needs to believe it has the machine to itself.

You could give each app a VM, but that means a full kernel each. You could give each app its own user account, but that hides little. We need something in the middle: the kernel lying politely.

From the course

The course names three technologies at the core of a container: namespaces (private views), control groups (limits) and union file systems (stacked files).

A namespace wraps a global system resource so that processes inside it appear to have their own isolated copy of that resource, and cannot see what happens outside their copy. The course gives two main examples.

The PID namespace. A PID is a process ID (the number the kernel gives each running program). Inside a container, your process appears to be PID 1 (the first process), even if the host has tons of other processes. From inside, you know nothing about them.

The user namespace. This maps a user inside the container to a different user on the host. You can run as root (the all-powerful administrator account) inside, while that user is a normal account outside. This matters for security. If an attacker breaks out of a container, they do not keep root's power on the host.

Correction

The course makes the protection sound close to automatic if "configured correctly". The important detail is that plain Docker Engine does not turn this on by default. Unless someone enables userns-remap or runs rootless mode, root in a container is the same user ID 0 as root on the host. The namespaces and other limits restrain it, but one mistake can make that power real.

Hypothetical scenario

Workload. The Python and Node.js services both listen on port 8080 by default.

Check yourself

PredictTwo containers both run a server on port 80 with no published ports. Does the second one fail?

No. Each has its own network namespace, so each has its own port 80. A clash happens only if both try to publish the same host port.

DiagnoseFrom inside a container, curl localhost:5432 fails, although Postgres runs in another container. Why?

Challenge"A container is secure because it can't see anything." Reply?

Control groups: what a process can use

Namespaces build the walls. Control groups meter the electricity.

The one ideaNamespaces decide what you can see. Control groups decide how much you can use.

The problem

From the course

Without limits, one greedy application can starve the others. The course calls this the noisy neighbour problem. A namespace does nothing here, because a process that cannot see its neighbours can still eat all the memory they need.

Control groups, or cgroups, are a Linux kernel feature that lets you put processes into groups, and then limit and monitor their access to resources. The resources include CPU, memory, storage devices and more. With cgroups you can isolate each application from a performance point of view.

Added explanation

A cgroup is a small set of rules with a list of member processes. The kernel checks those rules each time it hands out CPU time or memory. Every process belongs to a cgroup, and when a process starts a child, the child joins the same group. So a container cannot escape its limit by creating more processes.

Shares, limits and what the course's example really means

From the course

The course gives an example. One application may use up to 30% of the CPU cycles, set with cpu.shares. It may use up to 50 megabytes of memory, set with memory.limit_in_bytes. Its disk reads can be limited with the block IO throttle setting for read bits per second.

Correction

Three details in that example

cpu.shares is not a percentage or a cap. It is a relative weight. It only matters when CPUs are busy and processes compete. A hard ceiling is a different setting: Docker's --cpus flag. The course repeats this idea later when it says --cpu-shares sets a percentage of CPU cycles. Docker's own help text calls it a relative weight.

"bps" means bytes per second, not bits, in the kernel's blkio.throttle.read_bps_device.

Those are cgroup v1 names. Most new Linux systems use cgroup v2, where the same ideas are called cpu.weight, cpu.max, memory.max and io.max. Docker deprecated support for v1 in version 29, and has promised it until at least May 2029. Also, the live settings are in the /sys/fs/cgroup file system. /proc/cgroups only lists the kinds of controller available.

CPU and memory limits fail in very different ways, and this is worth remembering.

Too little CPU makes you slow. The kernel just gives your process less time. Nothing crashes, but requests take longer.

Too little memory makes you dead. Memory cannot be taken back gradually. The exit code 137 means the process was killed with signal (a small message from the kernel) number 9, because 128 + 9 = 137. The course says "Docker will kill it". To be exact, the kernel does it, and Docker reports it.

Union file systems: why images are practical

Namespaces and cgroups make containers possible. Layers make them cheap.

The one ideaA union mount stacks read-only layers and shows them as one folder. Writes go to a thin top layer. This one trick gives you small downloads, fast starts and shared disk space.

The problem

Added explanation

Each container needs a complete set of files. If each one had a full copy, a hundred containers of a 200 MB image would cost 20 GB of disk, and each start would mean copying 200 MB. The speed advantage would vanish.

From the course

The third technology is a union mount file system (a way to show several folders as one). The one Docker uses is called overlayfs (the Linux file system that stacks layers). It takes separate file systems and combines them into one view.

The course's slide shows a lower layer with files 1, 2a and 4, and an upper layer with a different file 2b, a new file 3, and file 4 deleted. In the combined view, the upper layer wins. You see file 1, file 2b and file 3.

The course sums it up well: namespaces and cgroups make containers possible, and the union mount makes them practical. With layers, many images can share common lower layers, and only some upper layers differ. So you move less data to get an image onto a system, and you use less space when running many copies.

Added explanation

Three mechanisms make this work.

Layers are read-only and identified by a hash (a fingerprint computed from the content). If two images contain the same layer, the host stores it once.

Copy-on-write (keep sharing a file until someone changes it). A running container gets one thin writable layer on top. Reading a file finds it in a lower layer, at no cost. The first time you change a file, the kernel copies it up into the writable layer, and the change happens there. The lower layer stays untouched.

Whiteouts (marker files that hide a file). You cannot erase a file from a read-only layer. So a delete adds a small marker file in the upper layer, and the combined view hides the file. The bytes remain in the lower layer. Chapter 15 shows why this is dangerous for secrets (passwords and keys).

Lab: what a container really changed$ docker run --name df lab/base sh -c 'echo x > /newfile; echo y >> /etc/passwd; rm /etc/group'$ docker diff dfA /newfileC /etcC /etc/passwdD /etc/groupA = added, C = changed, D = deleted. Only these live in the writable layer.
Correction

Where layers are stored has changed

The course describes overlayfs through Docker's classic storage driver. Since Docker Engine 29, new installs use the containerd image store by default. It uses a component called a snapshotter in place of the classic overlay2 driver. Existing installs are not forced to move. The idea of stacked layers stays the same, and on Linux it is still overlayfs underneath (the test machine reported overlayfs with the io.containerd.snapshotter.v1 driver type). Only the plumbing and the disk paths changed.

Where it stops being accurate. Sheets are physical, so two projectors cannot share one. Layers can be shared by thousands of containers. Also, the tape hides a word from view, but the word is still there underneath, and that part of the analogy is exactly right.

Hypothetical scenario

Challenge"Copy-on-write must be slow." Reply?

Reads have almost no cost, and most container files are only read. The cost appears on the first write to a big existing file. That is one more reason to keep heavy write work, such as databases, on volumes (storage that outlives a container).

You can use namespaces and cgroups directly. Docker packages them so you do not need to know all the commands to create control groups or namespaces. You get an application you install and a few simple commands.

The client application. The Docker CLI (command-line interface, where you type commands) is what runs when you type docker run. Data: what survives and what does not

Containers are built to be thrown away. So you must decide where each piece of data lives.

The one ideaBy default, anything a container writes dies with the container. Put each kind of data in its proper home: the image, a volume, or a bind mount.

The rule, and the three kinds of data

From the course

By default, any data you create or change inside a container at run time is ephemeral (short-lived). If the container is stopped and removed, the data is gone. At run time the image layers are read-only, and a thin read-write layer sits on top. That is where changes go.

The course separates the cases:

  • Dependencies and configuration you know about at build time. Build these into the image, so that every container has them.
  • Data the application creates at run time. A user edits a profile, and it goes into a database. You cannot put that in the image, because you do not know it at build time. It must outlive the container.

Experiment 1: install something, lose it

From the course

The instructor makes this concrete. He starts an Ubuntu container with a shell:

docker run --interactive --tty --rm ubuntu:22.04

--interactive and --tty give you a working shell inside. --rm tells Docker to delete the container once it exits. Inside, ping google.com fails because ping is not installed. So he runs apt update and apt install iputils-ping, and ping works.

He exits and runs the same command again. The new container has a different ID. It knows nothing about the old one, and ping is gone again.

Next he removes --rm and adds --name my-ubuntu-container. He installs ping and exits. The container is stopped but not removed, so docker ps -a still lists it. docker start brings it back, docker attach reconnects, and ping still works. The read-write layer survived, because the container was never removed.

He then warns that you would never normally do this. The correct approach is to build it into your own image:

docker build --tag my-ubuntu-image -<<EOFFROM ubuntu:22.04RUN apt update && apt install iputils-ping --yesEOF

Now every container made from my-ubuntu-image has ping from the start.

Experiment 2: data made at run time

From the course

He creates a folder and a file inside a container, exits, and starts a new one. The file is missing. This time, a Dockerfile cannot help, because you do not know the content in advance. Two mechanisms exist for this: volumes and bind mounts.

Volumes. docker volume create my-volume makes a storage location managed by Docker, under /var/lib/docker/volumes on the Docker host. On a Mac or Windows laptop that path is inside the virtual machine. Then you mount it:

docker run -it --rm --mount source=my-volume,destination=/my-data/ ubuntu:22.04

He writes the file, exits so that the container is removed, and starts a new container with the same volume. The file is still there. The volume has a life of its own.

Since he is on a Mac, /var/lib/docker/volumes is not on his own disk. He uses a privileged container to get a shell in Docker's VM and finds his file there, in the volume's _data folder. The course's repository names the trick: an image called justincormack/nsenter1, run with --privileged --pid=host.

Bind mounts. Here you connect a folder on your own machine into the container:

docker run -it --rm \  --mount type=bind,source="${PWD}"/my-data,destination=/my-data \  ubuntu:22.04

A file written inside appears on the host, and a change on the host appears inside. It works in both directions, because both sides are looking at the same folder.

Which one? Docker suggests volumes by default. A bind mount crosses the boundary between the VM and your host, so heavy reading and writing can be much slower. A bind mount is good when you want to see the files easily. Later the course uses one to mount source code, so that edits appear inside a running container at once.

Added explanation

Three more facts save hours of confusion, and all were tested.

From the course

From the course

One caution. Mounting ~/.aws hands your cloud keys to that image. Only do this with images you trust, and pin the version. A convenient tool from a stranger is still a stranger's code running beside your credentials.

Writing a Dockerfile: the Node.js journey

Start with something that works. Then improve it, one reason at a time.

The one ideaEvery line in a Dockerfile adds a layer, and the order of the lines decides what can be reused. Good Dockerfiles put what rarely changes first.

The inputs

From the course

To containerise an app, you write a specification and build an image from it. The specification is a Dockerfile, a text document with all the commands to assemble the image. Think of it as a recipe. Start from a base such as an operating system. Install the language runtime and your app's dependencies. Set up the environment. Finish with a command that starts your app.

A Dockerfile is paired with a build context (the set of files a build may read), usually a folder of your source code. It can also be a URL, such as a public GitHub repo. docker build takes both and produces an image.

One more file matters. .dockerignore tells Docker which files to leave out. You never want your host's node_modules copied in, because the image installs its own, and the two can conflict.

The format is simple. # starts a comment. Instructions are written in capitals by convention, followed by their arguments. The Dockerfile reference in Docker's documents lists every instruction.

Version 0: naive but working

From the course
Dockerfile.0FROM ubuntuRUN apt update && apt install -y nodejs npmCOPY . .RUN npm installCMD [ "npm", "run", "dev" ]

He builds it up step by step, and hits real errors. apt install first fails because it asks a yes-or-no question, so it needs -y. npm install fails until npm itself is installed. Each command adds a layer, so he joins apt update and apt install on one line. He tags (names) the result with docker build -t api-node:0 .. Without -t, you only get a long ID.

The image is almost a gigabyte. He calls this Dockerfile functional and terrible. Then the improvements begin.

The improvements, in order

From the course

1. Use an official image. Docker Hub has official images for language runtimes, with Node ready to go. FROM node replaces the install step.

2. Pin a version. FROM node really means node:latest, and that tag moves when the maintainers push. So he pins an exact tag and picks a small one: node:19.6-alpine. Alpine is a very small Linux distribution. The image shrinks by a factor of five, to about 200 MB. A smaller base also has fewer utilities to attack.

3. Protect the cache. Each rebuild was slow, because copying all the source before npm install broke the cache on every edit. So copy only package.json and package-lock.json, run the install, and then copy the rest. That layer now breaks only when dependencies change.

4. Set a working directory. WORKDIR /usr/src/app keeps things tidy, away from the root folder.

5. Copy only what you need. .dockerignore excludes node_modules, and COPY ./src/ . brings in just the source.

6. Use the production command. npm run dev is for development, so CMD [ "node", "index.js" ] replaces it.

7. Do not run as root. The official image includes a user called node. USER node switches to it. COPY --chown=node:node makes sure that user owns the files.

8. Set NODE_ENV=production. Many Node packages behave differently when this is set.

9. Install exact production dependencies. npm ci is a clean install of the exact versions in package-lock.json, which is more repeatable. --only=production skips development tools such as Jest and nodemon.

10. Document the port. EXPOSE 3000 changes nothing about how the container runs. It is documentation for the people using the image.

11. Add a cache mount. With RUN --mount=type=cache,..., npm keeps its download cache between builds. If the layer does break, only new packages come from the internet.

Final Dockerfile, production path (course repository, shortened)FROM node:19.6-bullseye-slim AS baseWORKDIR /usr/src/appCOPY package*.json ./ FROM base AS productionENV NODE_ENV productionRUN --mount=type=cache,target=/usr/src/app/.npm \  npm set cache /usr/src/app/.npm && \  npm ci --only=productionUSER nodeCOPY --chown=node:node ./src/ .EXPOSE 3000CMD [ "node", "index.js" ]

Hypothetical scenario

Multi-stage builds: the Go API and the React client

The tools that build your program do not need to ship with it.

The one ideaA multi-stage build uses one big image to make something, then copies only the result into a small clean image.

The Go API

From the course

The Go journey starts the same way: FROM golang, WORKDIR /app, COPY . ., go mod download, and CMD ["go", "run", "main.go"]. That is over 900 MB. Pinning 1.19-alpine cuts it in half.

Then come Go-specific steps. go run builds and then runs on every start, so he builds once in the Dockerfile with go build -o api-golang, and the command just runs the binary. Start-up gets faster. His .dockerignore lists the Makefile, the README and any Dockerfile, so that editing those does not break the cache. As before, he copies go.mod and go.sum first and downloads dependencies before copying the source.

Now the new idea: a multi-stage build (one Dockerfile with several stages, where only the last one ships). For a compiled language, you need many tools to build, and the result is one binary. So he labels the first stage AS build, and adds a second stage:

The final stages, simplifiedFROM golang:1.19-bullseye AS buildWORKDIR /appCOPY go.mod go.sum ./RUN go mod downloadCOPY . .RUN go build -ldflags="-linkmode external -extldflags -static" \    -tags netgo -o api-golang FROM scratchENV GIN_MODE=releaseCOPY --from=build /app/api-golang api-golangEXPOSE 8080CMD ["/api-golang"]

scratch is a special empty starting point. COPY --from=build reads from the earlier stage and not from your host. The binary must be statically linked (it contains all the code it needs). The default was not, so he adds the linker flags. He also adds the netgo tag, which he found was needed to make networking work. The Alpine build stage then lacked the compiler needed for static linking, so he switched to a Debian-based one. A bigger build stage does not matter, because it never ships.

The result is 16.8 MB, down from about 500. He also sets GIN_MODE=release, documents port 8080, and adds cache mounts for /go/pkg/mod and /root/.cache/go-build. To drop root, he creates a user in the build stage, copies /etc/passwd to the final stage, and sets USER. He admits this may be over the top with so little in the image, but it adds one more layer of defence.

Correction

Small details

scratch is not a real image. The course shows a Docker Hub page for it and says it contains a valid root file system. To be exact, FROM scratch is a reserved word that means "start with no layers". You cannot pull it. The lab got: 'scratch' is a reserved name.

The user ID. The instructor says user ID 1000 aloud, while the file in his repository uses 1001. It makes no real difference.

An easier path. These linker flags keep CGO (Go's bridge to C code) turned on, and force a static result. Many Go projects avoid all this with CGO_ENABLED=0, which gave a static binary at once in the lab. This only works if your code and its libraries do not need C. The course does not cover it.

Versions. Go 1.19 and Debian Buster and Bullseye are all out of support now.

The React client

From the course

In development, a Vite app is a Node.js server, so the Dockerfile looks just like the Node API's. In production, you do not want a Node server at all. npm run build produces plain static files (HTML, JavaScript and CSS), and these need only a simple web server.

So this is a multi-stage build too. A Node stage (on a Debian-based tag, since it will not ship) installs and builds. A second stage starts from NGINX and copies in two things: the built files from dist, placed in NGINX's standard folder, and an nginx.conf from the host.

The config has three jobs. /ping returns 200 and the word "pong" directly. /api/golang and /api/node proxy (forward) requests to the API services. Any other path serves the React files.

Correction

Since Docker 20.10, containers start with net.ipv4.ip_unprivileged_port_start=0, so any user may bind any port. This applies to Docker, and Kubernetes does not default to it. So 8080 remains the safe choice if your image might run anywhere.

From the course

Parser directives go at the very top of a Dockerfile. # syntax=docker/dockerfile:1.5 selects a Dockerfile syntax version, needed for newer features. # escape= changes the escape character from the default backslash.

Registries and tags

How images leave your machine, and how to name them so that nobody gets a surprise.

The one ideaA tag is a label you can move. A digest is a fingerprint that can never move. Build your process around that difference.

What a registry is

From the course

So far all images were local. A team needs a container registry: a repository, or a collection of repositories, for storing and accessing images. You push images from your machine or from a continuous integration server (a system that builds and tests code automatically), and teammates and servers pull them. Repositories can be public or private. Docker Hub is a popular one, and GitHub, Google, Amazon and Azure all offer one.

For a public registry, pulling needs no login, and pushing does. A private one needs a login for both. Docker Desktop's credential helper keeps your logins in a safe system store, such as the macOS keychain. Some registries add their own tools. Google's used the gcloud command to log you in.

Pushing an image

From the course

To push, you need two things: you must be authenticated, and the image must have a tag that matches the repository.

For Docker Hub, he makes a repository my-scratch-image, runs docker login, and retags his local image:

docker tag my-scratch-image sidpalas/my-scratch-imagedocker push sidpalas/my-scratch-imagedocker tag my-scratch-image sidpalas/my-scratch-image:abc123docker push sidpalas/my-scratch-image:abc123

With no tag given, latest is assumed. For GitHub's registry, he creates a personal access token with the write:packages permission and logs in by piping the token to docker login ghcr.io. Then he tags with the ghcr.io/ prefix and pushes. He revokes the token afterwards. Each registry has its own login steps, so follow its own instructions.

Tagging well

From the course

Leaving the tag off is bad practice, because latest tells you nothing. Use descriptive tags. One image can hold many tags: when the instructor checked Docker Hub, five names, including ubuntu:latest, ubuntu:22.04, ubuntu:jammy, ubuntu:jammy-20221130 and a sha256 hash, all pointed to the same image.

Treat tags as immutable. Do not build, tag, push, then rebuild and overwrite that tag. Someone using it can get the new version by accident. The exception is a temporary local tag.

In a CI system, people often combine several of these:

  • a timestamp, for example 20221130
  • a build ID from the CI system
  • the commit hash (the ID of a saved code change) of the source
  • a semantic version (a number in major.minor.patch form) such as 1.1.0
Correction

Registry updates

Google Container Registry (gcr.io) has been shut down in favour of Artifact Registry. The course's example is out of date, though the idea of using a provider's own tool to log in remains right.

Passwords. The course mentions a Docker Hub username and password. Use an access token in place of your password, as its CI chapter does.

Tags can be protected. Several registries can enforce immutable tags, so this does not depend on good behaviour alone. Turn it on if you can.

Why --init exists

From the course

Some programs are not designed to run as process ID 1, which is what happens by default in a container. With --init, Docker runs its own small init program as PID 1 and starts your program as a child. In the demo, ps shows docker-init as PID 1 and ps itself as PID 7. This helps when your app manages subprocesses, because it makes it easier to forward termination signals.

In the course's Docker CLI module, the instructor runs docker run ubuntu sleep 999, presses Ctrl+C, and nothing happens. He ends it with docker kill from another terminal.

Added explanation

These two moments are the same fact, though the course does not join them up. A signal is a small message the kernel delivers to a process, for example "please stop". On Linux, PID 1 is special: if it has no handler for a signal, the kernel drops the signal. Other processes would simply die. So sleep as PID 1 ignores both Ctrl+C and docker stop.

docker stop sends SIGTERM, waits (10 seconds by default), then sends SIGKILL. docker kill sends SIGKILL at once. An init process also collects zombie processes (finished child processes that nobody has tidied up).

Container security

A container is not secure by default. It is securable.

The one ideaSecurity comes in two halves. Image security reduces what can be attacked. Runtime security limits what an attacker can do after they get in.

The false comfort

From the course

The instructor's favourite meme in the course shows a Cheeto used as a lock. Just because something runs in a container does not make it secure. If you use --user root, --privileged and the host network, you remove almost all of the boundary a container provides.

There are two areas. Image security is about what you build in, especially software dependencies and attack surface. Runtime security asks: if someone compromises your container, what can they do? Can they escape and move sideways to the host and other containers, or are they stuck?

Image security

From the course
  • Keep the attack surface small, with a minimal base image. Chainguard is one source of security-focused bases.
  • Leave out anything not needed in production, and use multi-stage builds for what you need only at build time.
  • Scan your images. Docker had one built in, using Snyk, and Trivy from Aqua Security is another. You then decide if you must patch or can accept a known flaw.
  • Run as a non-root user with minimal permissions.
  • Keep credentials out of the image. Treat every image as if it were public, and inject secrets at run time.
  • Sign your images, to prove who built them.
  • Pin base images at least to the minor version, so that bug-fix patches arrive while breaking changes hopefully do not. Or use the image hash to lock it completely.

Runtime security

From the course
  • On the daemon, turn on the user namespace remap option, so containers run in a separate user space.
  • Set the file system to read-only if the app does not need to write.
  • Use --cap-drop=ALL, then add back only what you need.
  • Limit CPU and memory, to prevent a denial of service (one thing using up everything, so that others fail).
  • Use seccomp or AppArmor profiles (rule sets that limit what a process may ask the kernel to do).
Correction

What has changed

docker scan is gone. The command that used Snyk has been removed, and the lab's CLI reports it as unknown. Docker's current tool is Docker Scout, which comes with Docker Desktop. Trivy remains a good free choice.

Signing. Docker is retiring Docker Content Trust, the older signing system. Signing certificates for Docker Official Images began to expire in August 2025. Docker points publishers to Sigstore or Notation.

Pinning at the minor version is a fair default, as long as you also rebuild regularly. A tag can move, so only a digest truly locks it.

Defaults help. Docker already drops many capabilities and applies a default seccomp profile, which blocks around 44 system calls. Those defaults are why --privileged and --security-opt seccomp=unconfined are such bad habits.

Added explanation

Reasoning about this is easier with the phrase defence in depth (several layers of protection, in case one fails). Assume each layer can fail, and have the next one ready. Non-root stops an attacker from installing tools. Dropped capabilities stop them from changing the network. A read-only file system stops them from saving anything. No single setting is the answer.

There is one danger the course mentions only in passing. Mounting /var/run/docker.sock into a container gives it control of the Docker daemon, and that means root on the host. Docker's documents warn that even the docker group gives root-level power. Be careful with this.

Hypothetical scenario

Ledgerline: a breach that went nowhere

Hypothetical event. A flaw in a third-party library lets an attacker run code in an API container.

Architecture. Distroless image, non-root user, --cap-drop=ALL, read-only root file system, one small temporary folder, and memory and process limits. The container sits on an internal network that can reach only the payments database.

Sequence. The attacker finds no shell and no package manager. They cannot write to disk, and a process flood hits the --pids-limit. Logs show unusual errors, and an alert fires.

Trade-offs. It took weeks to find every path the app wrote to. Debugging is harder. Layers bought time and a loud alarm, and that is what they are for. None of this fixes the original flaw, and the database credentials inside the process are still at risk, so the team rotates them.

Check yourself

ExplainName the two halves of container security, with one example each.

Image security, such as a minimal base image. Runtime security, such as --cap-drop=ALL.

PredictAn app runs fine as root but crashes with --read-only. What is the likely cause, and the fix?

It writes somewhere, perhaps to /tmp or a cache folder. Add a small --tmpfs or a volume for only that path.

Challenge"We scan our images, so we're secure." Reply?

A scanner only knows published flaws in the packages it can see. It cannot find your own bugs, and it does nothing at run time. Scanning is one layer.

Images

From the course

The instructor says he rarely uses import, load or save, since his images come from Dockerfiles.

Correction

Two definitions

Dangling. The course says docker image prune removes any image not linked to a container. By default it removes only dangling images, which are untagged layers left over from rebuilds. You need -a to remove all images that no container uses. The help text confirms this.

Save and export. The course says load takes an archive made by "docker save on a container". docker save works on images. docker export is the one for a container's file system, and docker import is its partner. They are different: save keeps layers and metadata, while export flattens everything.

Containers

From the course

attach connects your terminal to a running container's streams. exec runs a new command inside one, which is usually what you want. logs prints output, and -f follows it live. top lists its processes. wait blocks a script until the container exits and prints the exit code. ls is the same as docker ps, and -a adds stopped containers. stop is graceful, and kill is not. rm removes one, and prune removes all stopped ones.

Volumes and networks

From the course

Volumes have five actions. docker volume ls showed named volumes and many anonymous volumes (volumes with random names made by Docker). If you care about the data, use a named volume, because it is much easier to manage. Networks add connect and disconnect, which attach a running container to a network. He prefers to set the network in Compose or docker run.

Added explanation

A disk filling up is the classic Docker problem on a long-running host. Two commands help: docker system df shows what uses the space, and docker system prune cleans up. Read what it says before you agree. Volumes are not removed unless you add --volumes, and that is deliberate, as that is where your data lives. On containerd-store hosts the numbers and paths may look different.

Bazaar Box: the 2 a.m. disk alert

Trade-offs. Cleaning too much slows the next build, because cached layers must be rebuilt. They tune the filter to balance disk against speed. They do not touch volumes in automation, since a mistake there destroys data.

The idea

From the course

Continuous integration, or CI, means that each push to your version control system runs automatic pipelines that test, build and push your images. GitHub Actions is the CI system built into GitHub. You add a YAML file under .github/workflows, and in about 50 lines you get a working pipeline. The course does this for one service as an example.

  1. Checkout, a public action from GitHub.
  2. Docker metadata, an action from Docker that generates tags from the branch, pull request, version, and date plus commit hash.
  3. Login to Docker Hub, using a username and access token stored in the repository's secrets.
  4. Build and push, another Docker action, pointed at the Dockerfile and context, and applying all the tags.
  5. Trivy, set to fail the run if it finds any critical vulnerability.

Three things to improve

Scan before you publish. The workflow pushes first and scans after. So a flawed image is already in the registry, under latest, when the check fails. A safer flow builds locally, scans, and pushes only on success. The course does not discuss this order.

Choosing how to deploy

The same image runs almost anywhere. That freedom is both the blessing and the curse.

The one ideaChoose a platform by what you must not get wrong: security, ergonomics, scale, storage and cost. The image stays the same either way.

So many options

From the course

Containers give a standard interface, so many cloud providers will happily run your image. The course cites a 2021 article by Corey Quinn listing 17 ways to run containers on AWS alone, from serverless options such as Lambda, to Elastic Container Service, to Kubernetes. Portability gives flexibility, and it can also be overwhelming.

The course gives five questions to ask:

  • Security. Does the provider set safe run-time options, or at least give you the controls?
  • Ergonomics (how pleasant it is to use). Three parts: how easy is it to get from images to internet traffic, to release new versions, and to work with running containers, such as logs, monitoring and traces?
  • Scalability. Does it meet the size you need, per container and in total? Can you get GPUs? Can you span hosts, and how do services find each other?
  • Persistent storage. If containers can land on any machine, how do they reach their data?
  • Cost. At one end is bare metal: you pay only for compute and do all the work. At the other end is a managed platform as a service (a product that runs your app for you): you pay a premium for the comfort.

He built three deployments: Railway, Docker Swarm and Kubernetes. Only Swarm is in the main video, and the other two are bonus videos, so this guide does not cover their details.

Why not just use Compose on a VM?

From the course

You could, and it would work. But Compose has major limits for production:

  • No zero-downtime deploys. A new version means stop, then restart. It may be only a second or two, but it is downtime.
  • No easy rollback.
  • No encrypted secrets. The password has been a plain environment variable.
  • One host only. You cannot grow to several hosts or add high availability (staying up when a machine fails).

Two older objections no longer apply. Compose once lacked health checks, and it once lived in a separate binary. docker compose is now part of the Docker CLI.

Docker Swarm, built into Docker, addresses all four limits: rolling deployments, rollback, secrets and many hosts. Its config is nearly the same as Compose.

Correction

Fine print

Name. The course says "Elastic Kubernetes Engine". Amazon's product is Elastic Kubernetes Service (EKS). Google's is Google Kubernetes Engine.

Compose. docker compose is a CLI plugin, so "built into the binary" is loose wording. Compose does have a secrets key, but it only mounts a local file or environment value. It adds no encrypted store, so the course's point holds.

Swarm today. Swarm mode is still built into Docker Engine. Do not confuse it with the older standalone "classic Swarm". Docker's v29 announcement also said that its new nftables firewall support could not be turned on for a node with Swarm enabled.

Added explanation

Here is a judgement that the five questions lead to. A small internal tool with a few users may be perfectly fine on one VM with Compose and a brief restart. Downtime has a price, and if that price is low, the simplest thing wins. Do not reach for Kubernetes to feel safe. Equally, do not stay on one VM once a machine failure would cost you real money.

Hypothetical scenario

Bazaar Box: picking a platform

Constraints. Two operations engineers. The festival needs 20 times normal traffic for three days. The team knows Docker and Compose well.

Options. Kubernetes has the biggest ecosystem, but they have no one who has run it. A platform as a service is easy, but expensive at peak, and they need a custom network setup.

Decision. Move the database to a managed service. Run the stateless services on Docker Swarm, with a clear exit path to managed Kubernetes.

Trade-offs. Swarm's smaller community means fewer ready-made answers. Their images and health checks would move to Kubernetes unchanged. Only the deployment files would need rewriting. The image is the safe bet, and the platform is replaceable.

Check yourself

ExplainName the course's five questions for choosing a platform.

Security, ergonomics, scalability, persistent storage and cost.

Challenge"Everyone uses Kubernetes, so we should too." Reply?

Kubernetes solves real problems of large fleets, and it costs real effort. Start from your needs and your team. Your images will still run there if you outgrow something simpler.

Deploying with Docker Swarm

One virtual machine, four services, secrets, rolling updates and health checks.

The one ideaA production deployment is a description of the state you want, plus a health check that tells the system when it has got there.

The plan

From the course

To keep things simple, the swarm is one VM, so it is similar in concept to docker compose up. The steps are:

  1. Create a VM and open the firewall.
  2. Install Docker Engine, and connect your laptop's client to it.
  3. Start the swarm.
  4. Adapt the Compose file.
  5. Add secrets, a deployment strategy and health checks.
  6. Push images and deploy.

He gives a clear warning about the database. It runs in the swarm with a volume, so data survives restarts. But there are no backups. If user data matters, add periodic backups with tested restores, or use a database as a service such as Amazon RDS or Google Cloud SQL.

Preparing the host

From the course

He creates a small Ubuntu VM with a public IP address (its address on the internet) on Civo, though any cloud works. He attaches a firewall that allows SSH (secure remote login) on 22, web traffic on 80 and 443, and 3000 and 8080 to reach the APIs directly. An all-open test rule is turned off.

Over SSH he installs Docker Engine with the script at get.docker.com. docker ps then fails with a permission error on the Docker socket, so he changes the socket's ownership with chown.

Then the neat part: he exits SSH and keeps using the CLI on his laptop.

export DOCKER_HOST=ssh://ubuntu@<vm-ip>docker ps            # runs on the laptop, talks to the VM's daemondocker swarm init

This works because Docker is a client and a server, and the client can reach a remote daemon over SSH.

Correction

Host setup, done properly

The install script. Docker's documents recommend the convenience script only for test and development machines. For production, use the package repository method.

The socket. Changing its owner by hand will not survive a daemon restart, since the socket is created again at start-up. The normal way is adding your user to the docker group. Either way, remember that access to the socket gives root-level power. Protect it like root.

Firewalls. A cloud firewall sits outside the VM, as the course uses. A firewall on the VM, such as ufw, is different: Docker's documents warn that published container ports bypass ufw and firewalld rules.

Close the test doors. Ports 3000 and 8080 were opened for testing. Close them when you finish, so that traffic has to pass through NGINX.

Contexts. docker context create is a tidier way to save a remote host than an environment variable.

From the course

He copies the Compose file and renames it docker-swarm.yml. He removes the Vite service, since it was only for development. He removes every build: block, because Swarm runs images and does not build them. Each service now names an image pushed to Docker Hub, with exact tags: client 5, Node 9, Go 8. Ports stay as 80:8080 for the client, and 3000 and 8080 for the APIs.

docker stack deploy first complains that the file needs a version, so he adds version: '3.7'. Then it warns that restart is not supported, since Swarm handles restarts in its own way, so he removes it. Because Swarm is declarative (you state the result, and the system works out the steps), he just deploys again over the top, and it reconfigures itself. The app is live on the VM.

Secrets

From the course

Next he fixes the credentials. Secrets are created by a separate process, so that they never sit in your Git repository:

In the stack file, a top-level secrets: block marks them as external: true, meaning they were created elsewhere. Each service lists the ones it needs. A secret arrives as a file, mounted in memory at /run/secrets/<name>. So his apps needed a small change: read the value from an environment variable, or else from a file whose path is in DATABASE_URL_FILE. The official Postgres image already supports POSTGRES_PASSWORD_FILE.

His first attempt fails. The APIs cannot connect. Checking inside a container, he finds a stray -n in the secret. He had used echo -n to avoid a newline, and the -n itself was saved. Switching to printf fixes it. He redeploys and all is well.

From the course

To deploy without stopping the old version first, he adds a deploy section to each service. It sets mode: replicated and a number of replicas (running copies). Three worked cases, and when not to use containers

All the ideas together, in three different settings. Everything in this chapter is hypothetical.

The one ideaGood container design is mostly about one question: when this part fails, what happens next?

Hypothetical scenario

Case 1. Bazaar Box survives the festival

Workload. A shop with a React storefront, catalogue and checkout APIs, and PostgreSQL. Normal traffic is 200 requests a second, and the festival peak is 4,000.

Constraints. Two operations engineers, a three-day peak, and no tolerance for lost orders.

Architecture. A managed PostgreSQL service with backups. Docker Swarm on six VMs: three managers and workers mixed, for quorum. Stateless services with four to twenty replicas. NGINX in front. Images pinned by tag and built in CI. Secrets in Swarm. A frontend and a backend network.

Preparation. They load-test to find real memory use, then set --memory limits a little above it. They give checkout more CPU shares than catalogue, so that during a fight for CPU, checkout wins. They raise replicas two days before the sale.

Sequence of events. Day two, 19:40. Traffic hits 3,600 requests a second. A memory leak in catalogue, triggered by a new search filter, slowly fills the container. One by one, catalogue tasks hit their limit and are killed with exit code 137. Swarm starts replacements in seconds. Customers see slightly slow search and no outage. The limit turned a server-wide crash into a small, contained restart loop.

The fix. An engineer finds OOMKilled true in the logs, builds a fix, and pushes a new tag through CI. They deploy with start-first. Health checks pass, old tasks drain, and the leak stops, all during peak.

Trade-offs. Over-provisioning cost extra for three days. Only the managed database made this calm: if it had been a container on one VM, the riskiest part would also have been the least protected. Their replacement loop also hid the leak for a while, so they add an alert on restart counts.

Hypothetical scenario

Case 2. Ledgerline protects each transaction

Workload. A payments API. A customer's money must move exactly once.

Constraints. An outage is bad. A double charge is worse. Every release must be safe during live traffic.

The first problem: stopping. A docker stop sends SIGTERM, waits ten seconds, then kills. A payment in progress could be cut off. So the app handles SIGTERM: it stops taking new work, finishes what is running, then exits. They use init: true, the exec form of CMD, and a longer stop_grace_period of 30 seconds, tested with real load.

The second problem: retries. A killed request may have succeeded. So each payment carries an idempotency key (a unique ID that lets the server spot and ignore a repeat of the same request). A retry cannot charge twice. Containers can fail at any moment, so the app must be safe at any moment.

The third problem: two versions at once. start-first means old and new code run side by side. In one release, the new version renames a database column, and the old version crashes. So they adopt expand and contract: add the new column, deploy code that uses both, move the data, and remove the old column in a later release. Each step is safe with the versions around it.

Failure behaviour. A release fails its health check in testing. Automatic rollback restores the old image. But rollback changes only the code. It does not undo a database migration. That is why migrations must stay backward-compatible.

Trade-offs. Releases take longer and need more thought. In exchange, deploying during business hours is boring, and that is the goal.

Hypothetical scenario

Case 3. Meridian Group runs a shared platform

Workload. 300 developers and 400 services across several business units, on shared infrastructure.

Constraints. One team must not hurt another. Regulators want evidence. Budgets are tight.

Architecture. Managed Kubernetes, because the scale justifies it. A central registry. A paved road (a supported default way of doing things): approved base images, a shared CI template, and default limits.

Rules, each tied to a mechanism.

  • Every workload has CPU and memory limits, enforced at admission. (cgroups, and the noisy neighbour.)
  • No privileged, no host network, non-root by default. (Namespaces and capabilities.)
  • Sensitive workloads run on separate node pools. (Containers share a kernel, and VMs do not.)
  • Images must come from the central registry, signed, with a scan report. (The supply chain.)
  • Third-party CI actions are pinned to commit hashes. (The Trivy incident in Chapter 22.)

Sequence of events. A team's batch job begins to use every CPU on its nodes, because it has no limit. Latency rises for three other teams. The platform team traces it to the missing limit in a namespace that skipped the rule. Admission rules now reject any pod with no limit. The job team is annoyed for a day, and nobody else is hurt again.

Trade-offs. A platform team is a real cost, and rules slow down teams with unusual needs, so there is a documented exception path. They also pay for Docker Desktop, or provide an alternative, since a company of their size falls outside the free terms.

When not to use containers

Added explanation

Containers are a tool, and judgement includes leaving a tool in the box.

  • A static website. Files on a content delivery network need no running process at all.
  • A small script on a schedule. A single cron job on a stable machine may not need any of this.
  • Software tied to a kernel or hardware. A kernel module, a device with no passthrough, or a program that needs a different kernel belongs on a VM or bare metal.
  • Your only database, if you cannot run it well. Containers do not provide backups, replication or tuning. A managed service is often the better choice.
  • When a VM gives the isolation you need. Running code from untrusted strangers on one shared kernel is risky. Use VMs, or a stronger sandbox.
  • When your team has one service and one server. A simple deploy script may serve you well for years.

The course's own message fits here: the point is repeatable software, and containers are one very good way to get it.

Twelve challenges you will hear, with answers you can give calmly.

Added explanation

Each answer rests on the mechanism. If you can rebuild the answer from the mechanism, nobody can shake you.

"A container is a lightweight VM." It looks similar from outside. A VM has its own kernel. A container is a process on a shared kernel, with a filtered view and limits. That is why it starts in about a second, and why it is weaker on isolation.

"Docker invented containers." No. Namespaces and cgroups are Linux kernel features. Docker's contribution was the image format, the registry habit and a good developer experience. The OCI then standardised the format.

"Containers are secure because they're isolated." The isolation is real but configurable. With --privileged, host networking and root, little remains. Security comes from layers you choose to keep.

"Containers are slower than bare metal." A container's code runs directly on the host kernel with no hardware emulation, so CPU cost is close to none. Real costs can appear in network or file-system paths, such as bind mounts on a Mac.

"The image contains an operating system." It contains the operating system's files. It has no kernel, and nothing boots. Ubuntu in a container is Ubuntu's programs on your host's kernel.

"Just use latest, it's simpler." latest is only a default name. It says nothing about freshness, and it can move. You cannot roll back to "latest".

"EXPOSE opens the port." It does not. It is documentation. -p opens a port, and the lab shows docker port is empty without it.

"I deleted the secret in the next line, so it's gone." A later layer only hides it. The lab recovered such a secret from a saved image.

"Set CPU shares to 30 to get 30%." Shares are relative weights, and they matter only under competition. For a hard ceiling, use --cpus.

"depends_on makes sure the database is ready." It only waits for "started" by default. Readiness needs a health check and condition: service_healthy.

"We have health checks, so we're fine." Plain Docker does nothing with them, and a check only proves what it tests. Swarm or Kubernetes acts on them. A shallow check approves a broken release.

"Volumes are backups." A volume survives a container. It does not survive a failed disk, or a mistaken delete. Backups are separate, and a backup you have not restored is only a hope.

Glossary

Every technical word in this folio, in plain English.

API: A way for one program to ask another program for data or actions.

AppArmor: A Linux tool that limits which files and actions a program may use.

Bare metal: Running software directly on a physical computer, with no virtual machine.

Base image: The starting image that your own image is built on.

Bind mount: A folder on the host shared directly into a container.

Blast radius: How much else breaks when one thing breaks.

Bridge network: A private virtual network that connects containers on one host.

Build context: The folder of files that Docker can read during a build.

BuildKit: Docker's modern engine for building images.

Buildx: The Docker command-line plugin for advanced builds, such as for several CPU types.

Capability: One small named piece of the root user's power.

cgroup: A Linux feature that limits and measures what a group of processes can use.

CI: Automatic building and testing each time code is pushed.

CMD: The Dockerfile instruction that sets the default command or arguments.

Commit hash: The ID of one saved code change in Git.

Compose: A tool that runs a multi-container app from one YAML file.

Configuration drift: Machines slowly becoming different from each other.

Container: A running process made from an image, with its own view of the system and limits.

Container runtime: A program that starts containers from images.

containerd: A background service that manages images and containers. Docker uses it.

Copy-on-write: Keep sharing a file until someone changes it, and only then make a private copy.

CSI: Container Storage Interface: a standard for connecting storage to orchestrators.

CVE: A publicly listed security flaw with an ID number.

Daemon: A program that runs in the background. dockerd is Docker's.

Declarative: You describe the result you want, and the system works out the steps.

Defence in depth: Using several layers of protection, in case one fails.

Dependency: Other software that your software needs.

Digest: A fingerprint of an image's content. It cannot be moved or faked.

Distroless: A very small image type with no shell or package manager.

DNS: The internet's phone book. It turns names into addresses.

Docker Desktop: An app for Mac, Windows and Linux with Docker, a VM and a GUI.

Docker Engine: The open-source core of Docker: the CLI, daemon and API.

Docker Hub: Docker's public registry of images.

Dockerfile: A text recipe for building an image.

ENTRYPOINT: The Dockerfile instruction that sets the main program of the image.

Environment variable: A named setting given to a program when it starts.

Ephemeral: Short-lived, and expected to be thrown away.

EXPOSE: A Dockerfile note saying which port the app uses. It opens nothing.

Health check: A small test that shows whether a container is working.

High availability: Staying up even when a machine fails.

Host: The machine that runs your containers.

Hot reload: The app updates by itself when you save a file.

HTTP: The language of the web. HTTPS is the encrypted form.

Hypervisor: Software that splits a computer into virtual machines.

Image: A sealed package of files and settings used to start containers.

Immutable: Cannot be changed after it is made.

Ingress: The entry point that receives traffic from outside.

Interpreted: Run by another program line by line, not compiled ahead of time.

IP address: A machine's address on a network.

JSON: A plain-text format for structured data.

Kernel: The core of the operating system. It controls hardware and processes.

Kubernetes: A popular orchestrator for running containers across many machines.

Layer: One saved set of file changes in an image.

Multi-architecture image: One image name that holds versions for several CPU types.

Multi-stage build: A Dockerfile with several stages, where only the last one ships.

musl: A small C library used by Alpine in place of glibc.

Namespace: A kernel feature that gives a process a private view of one resource.

OCI: The group that sets open standards for containers.

OOM killer: The part of Linux that kills a process when memory runs out.

Orchestrator: Software that places containers on machines and keeps them running.

overlayfs: The Linux file system that stacks layers into one view.

PID: Process ID: the number the kernel gives a running program.

PID 1: The first process in a namespace. Signals treat it differently.

Pipe: A link that sends one program's output into another program.

Port: A numbered door on a machine for network traffic.

Production: The real system that real users depend on.

Provenance: A record of where something came from.

Proxy: A program that forwards requests to another program.

Pull request: A proposed code change, waiting for review.

QEMU: An emulator that lets a computer act like a different CPU.

Raft log: The shared record that Swarm managers keep in agreement.

Registry: A storage service for images.

REPL: An interactive prompt where you type code and see the result.

Replica: One running copy of a service.

Reverse proxy: A server that receives requests and forwards them to other programs.

Rolling update: Replacing copies of a service a few at a time, to avoid downtime.

Root: The all-powerful administrator user on Linux.

scratch: The empty starting point for an image. It is a name, not a real image.

seccomp: A Linux filter that limits which kernel calls a process can make.

Secret: Sensitive data such as a password.

Semantic version: A version written as major.minor.patch, such as 1.1.0.

Signal: A small message the kernel sends a process, such as "please stop".

SSH: A secure way to log in to another computer.

Static linking: Putting all needed code inside one binary file.

Swarm: Docker's built-in orchestrator.

Tag: A movable name for an image version.

TLS: The encryption behind the padlock in your browser.

Union mount: Showing several folders as one.

User namespace: A namespace that maps user IDs inside a container to other IDs on the host.

Virtual machine: A software computer running inside a real one, with its own kernel.

Volume: Storage managed by Docker that outlives containers.

Whiteout: A marker file that hides a file from a lower layer.

Writable layer: The thin top layer where a running container saves changes.

YAML: A plain-text format for settings, based on indentation.

Zombie process: A finished process that nobody has tidied up yet.
