Example from one real toolchain: GCC 13 with its standard library on Linux. Other compilers and versions give different amounts.

  1. main.cpp goes into the preprocessor. It reads the text from top to bottom and carries out directives: lines that start with #.
  2. It finds one: #include <iostream>. That means: “replace this line with the whole text of the header file called iostream.”
  3. The iostream header includes other headers, such as <ostream> and <istream>, and those include even more. All of them get pasted in.
  4. The #include line is gone. In its place are thousands of lines of C++, including declarations that describe what the library offers. One of them says that an object named std::cout exists.
  5. Our own lines are copied through unchanged: a is still 5 and b is still 7. The preprocessor didn't check our C++, and it made no machine code.
  6. The result is one long piece of C++ text, called a translation unit. Next stop: the compiler, which needs all of it to understand what std::cout is.

  1. The compiler receives the translation unit: our code plus everything the preprocessor pasted in.
    2. 
          
  2. First it analyses the text. It splits it into tokens, like int, a, =, 5 and ;. Then it checks the grammar and builds a tree-shaped model of the code, called a syntax tree.
    3. 
          
  3. Next it checks the meaning. a and b are ints, so a + b is allowed. For std::cout << a + b it picks the version of << that prints an int.
    4. 
          
  4. Now it translates. Each part of main becomes a few machine instructions for one kind of CPU. These are for x86-64, a CPU family used in many laptops and desktop computers.
    5. 
          
  5. Look at the names with a question mark. std::cout and the printing code are in the C++ library, not in main.cpp, so the compiler can't know their addresses. It leaves gaps and writes notes for later.
    6. 
          
  6. The result is saved as an object file, main.o. (On some toolchains, a helper called an assembler does this last step.) Still nothing has run: 5 + 7 hasn't been worked out yet.

    3.

About stage 1

        
Source code

        

          

            
A programmer wrote this small program in C++, a programming language that people can read. The file, main.cpp, is plain text. The computer's processor can't run it as it is: tools must first turn it into machine instructions.

            

              
Input
The programmer's ideas, typed on a keyboard. No tool has touched the file yet.

              
What happens
The programmer writes C++ in a text editor and saves it as main.cpp.

              
Output
main.cpp: a plain text file of source code, 8 lines long.

              
Why it matters
Source code is how people describe what a program should do, in a form they can read, share and fix. Every later stage starts from this text.

            

            
Next stop: the preprocessor, which needs this text so it can carry out the #include line.

          

          

            

              
Common mix-up

              
Not quite: “I saved main.cpp, so now I have a program I can run.”

              
Actually: it's only text. Nothing has been added or printed. Several tools must work on it before the CPU can run anything.

            

            

              Look closer
              

                
Why can't the CPU read C++?

                
A CPU only understands machine instructions: tiny commands such as “copy this number”, “add these two numbers” or “jump to that address”, each stored as a few bytes. Different CPU families have different machine languages, such as x86-64 in many laptops and ARM64 in most phones. C++ is written for people, and it can be translated for many kinds of CPU.

                
What does '\n' mean?

                
It's the newline character. It moves the output to a new line after the answer is printed. Inside the computer it's stored as the number 10.

                
Why is main special?

                
Every ordinary C++ program needs a function called main. It's where the program's own work starts.

                
Is compiling the only way?

                
Some special tools, called interpreters, can run code without making an executable first. C++ is almost always compiled, and that's the path this journey follows.

About stage 2

        
The preprocessor

        

          

            
The preprocessor is a text tool that runs before the compiler. It carries out directives, the lines that start with #. Our only directive is #include <iostream>, so it pastes in the text of that header and of every header it includes. The result is still C++ text, just much longer.

            

              
Input
main.cpp, the source code (8 lines).

              
What happens
Each directive is carried out. The #include line is replaced by the contents of the header file it names.

              
Output
Preprocessed source, called a translation unit. It's still C++ text, and it's usually handed straight to the compiler instead of being saved as a file.

              
Why it matters
main.cpp uses std::cout but never says what it is. The pasted declarations tell the compiler that std::cout exists and how it can be used. Without them, the compiler would stop with an error.

            

            
Next stop: the compiler, which needs the complete translation unit to check our code against those declarations.

          

          

            

              
Common mix-up

              
Not quite: “The preprocessor checks my C++ and turns it into machine code.”

              
Actually: it only carries out # directives and edits text. It doesn't build a syntax tree, check what the program means, or make machine code. That's the compiler's job.

            

            

              Look closer
              

                
How much text gets pasted in?

                
It depends on the compiler and its standard library. With GCC 13 on Linux, for example, this one #include line pulls in about 185 header files, and the 8-line program grows to about 36,600 lines.

                
What's inside <iostream>?

                
Many declarations: promises that something exists, such as extern ostream cout;. The ready-made machine code behind std::cout usually isn't in the header. It has already been compiled and stored in the C++ standard library, which the linker uses later. Headers can also contain some code, such as templates and inline functions.

                
Other directives

                
#define FIVE 5 would make the preprocessor replace the word FIVE with 5 everywhere after it. #if and #ifdef keep or skip parts of the text. Our program only uses #include.

                
Line markers

                
Real preprocessed text contains marker lines such as # 3 "main.cpp". They remember where each line came from, so error messages can point at the right file and line.

                
See it for yourself

                
With GCC or Clang, the command g++ -E main.cpp prints the preprocessed text instead of compiling it.

              

            

            

              
Think about it

              
No line in main.cpp explains what std::cout is. So how does the compiler know about it?

              
Decide what you think first, then check.

              
              
The preprocessor pasted the iostream declarations into the text, including one that says an object named std::cout exists. When the compiler reads std::cout, that declaration is already there. The compiler still doesn't have the code behind std::cout: that comes from the library, during linking.

            

          

        

      


      
      

        
About stage 3

        
The compiler

        

          

            
The compiler is the translator. It reads the translation unit, checks that it follows the rules of C++, and translates our code into machine instructions for one kind of CPU. It works on one translation unit at a time, so it can't know where things defined elsewhere, like std::cout, will end up. It leaves gaps for later.

            

              
Input
The translation unit from the preprocessor.

              
What happens
The compiler analyses the text (tokens, grammar, meaning), reports an error if something is wrong, and translates the program into machine instructions for the target CPU.

              
Output
Object code: machine instructions plus notes about names and missing addresses, saved in the object file main.o.

              
Why it matters
A CPU can only carry out machine instructions from its own instruction set. This is the stage where readable C++ becomes those instructions.

            

            
Next stop: the object file, main.o, which keeps the result for the linker.

          

          

            

              
Common mix-up

              
Not quite: “It compiled, so the program has run, or it must be correct.”

              
Actually: compiling only translates. Nothing has been added or printed yet, and a program that compiles can still go wrong when it runs.

            

            

              Look closer
              

                
A quick tour inside the compiler

                
Tokens, then a syntax tree, then meaning checks, then optimisation, then code generation. Real compilers organise this work in different ways, and often use their own in-between languages, called intermediate representations.

                
What does “target-specific” mean?

                
The same a + b becomes different instructions for different CPUs. For x86-64, our example uses add eax, dword ptr [rbp-4]. For an ARM64 CPU, an addition can look like add w0, w1, w0: different names and different bytes.

                
What about optimisation?

                
With optimisation switched on (for example g++ -O2), a compiler can notice that a + b is always 12 and put 12 straight into the code. We show an unoptimised version so that every step stays visible.

                
Who writes the bytes?

                
Some toolchains, such as GCC, first write the instructions as text called assembly language, and then a tool called the assembler turns them into bytes. Others produce the bytes directly. Either way, the result is an object file.

                
Why leave gaps?

                
std::cout and the operator<< functions are defined in the C++ standard library. Thanks to the declarations, the compiler knows their names and types, but not where they will be in the finished program.

                
Two compilers, one mistake

                
Delete the semicolon after int b = 7, and GCC 13 reports “expected ',' or ';' before 'std'” at line 6, while Clang reports “expected ';' at end of declaration” at line 5. Same mistake, different words.

              

            

            

              
Think about it

              
If you forget a semicolon, which stage complains: the preprocessor or the compiler? Why?

              
Decide what you think first, then check.

              
              
The compiler. The preprocessor only carries out # directives and edits text; it doesn't check C++ grammar. The compiler checks the grammar, reports the error and doesn't make an object file. (The preprocessor has its own kinds of errors, such as a header file that can't be found.)

            

          

        

      


      
      

        
About stage 4

        
The object file

        

          

            
main.o is the object file: the compiler's output. It holds main's machine code, but it isn't a finished program. It also holds a list of names (symbols) and notes about missing addresses (relocations), which tell the linker what's missing and where to fill it in.

            

              
Input
The object code produced by the compiler (and, on some toolchains, the assembler).

              
What happens
Nothing is transformed here: this stage is a file, saved on disk. Its contents are organised into sections: code, symbols, relocation notes and more.

              
Output
main.o, waiting for the linker.

              
Why it matters
Big programs are built from many source files. Each one becomes its own object file, so after a change only that file needs compiling again. The extra information is what lets the linker join the pieces later.

            

            
Next stop: the static linker, which needs main.o's symbols and relocation notes to connect it with the library code.

          

          

            

              
Common mix-up

              
Not quite: “An object file is just machine code, and I can run it.”

              
Actually: it also contains symbols, relocation notes and other information, and its machine code still has gaps. It normally can't be run as a program.

            

            

              Look closer
              

                
Different systems, different object files

                
Linux uses .o files in ELF format. macOS also uses .o, in a format called Mach-O. Microsoft's Windows tools use .obj files in COFF format.

                
Coded names

                
Inside the file, C++ names are stored in a coded form called a mangled name. With GCC or Clang on Linux, std::cout is stored as _ZSt4cout, and std::ostream::operator<<(int) as _ZNSolsEi. Other compilers can use other codes.

                
Reading the bytes

                
c7 45 f8 05 00 00 00 means “store the 4-byte number 5 in a's spot”. x86-64 stores numbers smallest byte first, so 5 becomes 05 00 00 00.

                
Hexadecimal

                
Tools count in hexadecimal (base 16), with the digits 0 to 9 and then a to f. So 0x21 means 2 × 16 + 1 = 33, and 0a means 10.

                
Real numbers

                
With GCC 13 on Linux, for example, the real main.o for this program is 1,920 bytes long and has about a dozen sections. Its symbol table also lists a few extra names that our simplified view leaves out.

                
Look for yourself

                
On Linux, the tools nm, objdump and readelf show the real symbols, machine code and sections of an object file.

              

            

            

              
Think about it

              
main.o's symbol table says std::cout is undefined. Is that an error?

              
Decide what you think first, then check.

              
              
Not yet. It's normal for an object file to use names that are defined in other files. It only becomes an error if the linker can't find a definition anywhere.

            

          

        

      


      
      

        
About stage 5

        
The static linker

        

          

            
The static linker joins the pieces into one program. It takes main.o, some start-up code, and the parts of the static libraries that are needed. It matches every used name to its definition (symbol resolution), places everything in one program image, and fills in the missing addresses (relocation).

            

              
Input
main.o, start-up code supplied by the toolchain, and static libraries such as the C++ standard library and the C library.

              
What happens
Symbol resolution, copying in only the library pieces that are needed, combining sections, relocation, and recording the entry point.

              
Output
One executable file: add.

              
Why it matters
main.o alone has gaps and doesn't contain the code that actually prints. Linking produces one complete program that the operating system can load.

            

            
Next stop: the executable file, add, which waits on disk until someone runs it.

          

          

            

              
Common mix-up

              
Not quite: “The linker runs the program”, or “static linking copies in everything, even the operating system.”

              
Actually: the linker only builds a file. It copies in the library code that's needed, not whole libraries and not the operating system. Running happens later, in Stage 7.

            

            

              Look closer
              

                
What's a static library?

                
A bundle, or archive, of object files. On Linux it's usually a .a file, such as libstdc++.a for GCC's C++ library. Windows tools usually use .lib files. The linker copies in the members that define something the program needs, plus the members those need in turn.

                
Real numbers

                
With GCC 13 on Linux, for example, libstdc++.a holds 189 object files and the linker took 89 of them. It also took 554 of the 2,211 pieces of the C library. Printing a number needs more than you might think: locales, error handling and more.

                
Symbol resolution, in plain English

                
main.o says “I need std::cout.” The linker looks for a definition with exactly that name, finds it in a library piece, and connects the two. If there's no definition anywhere, it stops with an error such as “undefined reference” (Microsoft's linker says “unresolved external symbol”). Two definitions with the same name are an error too.

                
Relocation, in plain English

                
When main.o was made, nobody knew where std::cout would end up. Now the linker decides where everything goes. It follows each relocation note and writes the right address, or the distance to it, into the gap. In one real build of this program, a call's gap was filled with 18 0c 07 00. Read smallest byte first, that's 0x070c18: the code for operator<<(int) was 461,848 bytes further on.

                
Static or dynamic linking?

Many builds link the standard library dynamically by default. This journey uses static linking, for example with g++ -static.

                
Even static programs need the operating system

                
The operating system isn't copied in. When add runs, it asks the OS to do things for it, such as writing to the screen, using system calls. On Windows, even a statically linked program normally still uses system DLLs such as KERNEL32.dll, and on macOS every program uses the system library dynamically.

                
Start-up code

                
The toolchain adds a little start-up code that runs before main. On Linux with GCC it comes from files such as crt1.o, and the entry function is usually called _start.

              

            

            

              
Think about it

              
The C++ standard library has code for lots of things: files, text, maths, threads… Does our executable get all of it?

              
Decide what you think first, then check.

              
              
No. With static linking, the linker copies in only the library pieces needed to resolve our program's names, plus the pieces those pieces need. Unused parts, like regular expressions or threads, stay in the library.

            

          

        

      


      
      

        
About stage 6

        
The executable file

        

          

            
add is the finished program file. It holds everything the operating system needs to load it: a header with the entry point, loading instructions, the machine code and the data. But it's still just a file stored on disk, and it does nothing until someone runs it.

            

              
Input
The linked output from the static linker.

              
What happens
Nothing changes in this stage: the file waits on disk. Looking inside shows how it differs from main.o.

              
Output
An executable file on disk, ready to be loaded.

              
Why it matters
The operating system needs a complete program image, in a format it understands, with an entry point and loading instructions. main.o can't provide that. add can.

            

            
Next stop: the operating system, which reads add's header to load it and start it.

          

          

            

              
Common mix-up

              
Not quite: “Every program is an .exe file”, or “making the executable runs it.”

              
Actually: .exe files use Windows' PE format. Linux uses ELF and macOS uses Mach-O. And an executable is only a file until the operating system loads and runs it.

            

            

              Look closer
              

                
Same program, different formats

                
Linux: ELF, often with no file extension. Windows: PE, in a file ending in .exe. macOS: Mach-O. A program built for one system usually can't run directly on another, and an x86-64 program can't run directly on an ARM64 CPU. Use the buttons above the file to compare.

                
Why isn't the entry point main?

                
Before main, start-up code must prepare things: the stack, the C and C++ libraries, and objects like std::cout. So the entry point leads to start-up code, which later calls main. On Linux with GCC it's usually _start; with Microsoft's tools, mainCRTStartup. On macOS, the dynamic loader does the start-up work and then calls main.

                
Why is add so big?

                
Static linking copied in the library code it needs. With GCC 13 on Linux, for example, main.o was about 2 KB, the static add about 2.3 MB, and a dynamically linked version about 16 KB.

                
Optional extras

                
An executable may also contain a symbol table and debugging information. They help tools such as debuggers, but they aren't needed to run the program.

              

            

            

              
Think about it

              
You ask the computer to run add. Which part of the file does the operating system need to read first, and why?

              
Decide what you think first, then check.

              
              
The header. It shows that this is an executable in a format the OS understands and which CPU it's for, and it says where the loading instructions are and where execution should start: the entry point.

            

          

        

      


      
      

        
About stage 7

        
Loading and running

        

          

            
When you run add, the operating system creates a process, maps the program's code and data into memory, and starts the CPU at the entry point. The start-up code calls main, the CPU follows main's instructions, and the program asks the operating system to show 12 on the screen. The linker isn't involved any more.

            

              
Input
The executable file add, stored on disk.

              
What happens
The OS creates a process, maps the program into memory, prepares the stack and registers, and transfers control to the entry point. Then the CPU carries out the instructions.

              
Output
What the program does: the text 12 on the screen, and an exit status of 0.

              
Why it matters
A file can't do anything by itself. Only a process, a running instance of the program, actually carries out instructions.

            

            

              
Executable fileThe program stored as a file on disk, like a song file that isn't playing.

              
ProcessA running instance of a program, with its own memory. Run add twice at once and you get two processes.

              
RuntimeThe time while the program is running, and the environment it runs in.

            

          

          

            

              
Common mix-up

              
Not quite: “If it compiled and linked, nothing can go wrong.”

              
Actually: some problems only show up while the program runs, such as dividing by zero, using memory the wrong way, or a file that's missing. These are runtime errors. Imagine a version that reads b from the keyboard and works out a / b: if someone types 0, no compiler could have known.

            

            

              Look closer
              

                
On Linux, step by step

                
The shell usually creates a new process (with fork) and asks the kernel, the core of the OS, to load add into it (with execve). The kernel checks the ELF header, maps the parts listed in the program headers, builds the stack with the command-line arguments and environment, and jumps to the entry point.

                
If add were dynamically linked

                
The kernel would first start the dynamic loader (on Linux, ld-linux). It loads the shared libraries and connects them before main runs.

                
Mapping, not copying

                
The OS often doesn't copy the whole file into memory at once. It maps the file, and brings each part in when it's first needed.

                
Where does the answer go?

                
std::cout collects the characters in a buffer and hands them to the OS with a system call. On Linux, this program makes a single write request: 3 bytes, 31 32 0a, which are the characters '1' and '2' followed by a newline, sent to standard output. The terminal then draws them on the screen.

                
Exit status

                
return 0 from main tells the OS “success”. Other numbers usually mean something went wrong. In a Linux or macOS terminal, echo $? shows the exit status of the last program.

              

            

            

              
Think about it

              
You run add in two terminal windows at the same time. How many executable files are there, and how many processes?

              
Decide what you think first, then check.

              
              
One executable file on disk, but two processes. Each process has its own memory, its own a and b, and prints its own answer.

Words to know

  

    
Source code
Instructions written by a person in a programming language such as C++, stored as plain text.

    
Directive
A line starting with # that tells the preprocessor what to do, such as #include.

    
Header
A file of declarations (and some code) that other files can #include. <iostream> is a standard header.

    
Declaration
A statement telling the compiler that something exists and what type it is, such as extern ostream cout;.

    
Definition
The real thing a declaration promises: a function's code, or the place where an object is stored.

    
Preprocessor
The tool that runs first and carries out directives, for example by pasting in header files. It only edits text.

    
Translation unit
One source file after preprocessing: the complete text that the compiler works on.

    
Compiler
The tool that checks C++ and translates it into machine instructions for one kind of CPU.

    
Token
The smallest meaningful piece of program text, such as int, a, =, 5 or ;.

    
Syntax tree
A tree-shaped model of the program's structure that the compiler builds inside itself.

    
CPU
The processor: the part of a computer that carries out machine instructions.

    
Machine instruction
A tiny command for the CPU, such as “add these two numbers”, stored as bytes.

    
Register
A tiny, very fast storage place inside the CPU, such as eax.

    
Object file
The compiler's output file, such as main.o: machine code plus symbols, relocation notes and other information.

    
Symbol
A name in an object file, such as main or std::cout, marked as defined or undefined.

    
Relocation
A note saying “put the address of this symbol here”, and the linker's job of filling it in.

    
Static library
A bundle (archive) of object files. The static linker copies in the pieces a program needs.

    
Static linker
The tool that joins object files and library pieces into one executable, matching names and filling in addresses.

    
Dynamic linking
Keeping library code in separate shared files that are connected when the program is loaded or while it runs.

    
Executable file
A complete program file that the operating system can load and run, such as add on Linux or add.exe on Windows.

    
Entry point
The place in an executable where the CPU starts: usually start-up code, which later calls main.

    
Operating system
The software in charge of the computer, such as Linux, Windows or macOS. It loads programs and provides services like writing to the screen.

    
Process
A running instance of a program, with its own memory.

    
Stack
Memory that a running program uses as scratch space for its functions, for example to hold a and b.

    
System call
A request from a running program to the operating system, such as “write these characters to the screen”.

    
Runtime
The time while a program is running, and the environment it runs in.
