The big question

“One kind of chip starts the answer, and another kind does the rest.” True?

Half right. The real split is in the work, not the chip. Answering needs two kinds of work: reading your prompt (prefill) and writing the reply (decode). One GPU (the usual AI chip) can do both, and most systems still do.

Splitting them across machines is a design choice. Whether it pays depends on the workload (prompt length, reply length, number of users). It also depends on the cost of moving data between the parts, and on your goal. The goal might be a fast first word, fast typing, or low cost. Real designs now split the work in more than one way, even inside the writing step.

The spine of the guide

The Six Relationships

Six cause-and-effect rules explain almost every design in this guide. Every chapter names the ones it shows. The Bottleneck Meter tracks the first four, live.

R1Capacity decides what fits

Memory size sets what can sit next to the maths. That means the weights (the model's learned numbers), plus every user's saved chat notes. If they do not fit, you must split, shrink, or move data further away.

Example: Llama 3.3 70B needs 141 GB for weights at 16 bits per number. One H100 (a common NVIDIA AI chip, or GPU) holds 80 GB. So it cannot run on one H100 at 16 bits.

Signs: memory errors, fewer users than planned, long chats cut short.

R2Bandwidth decides how fast data arrives

Bandwidth (bytes moved per second) is the width of the road between memory and maths. Writing a reply rereads every weight at every step, so bandwidth sets typing speed.

Example: 70.6 GB of weights at FP8 (1 byte per number) ÷ 3.35 TB/s ≈ 21 ms per step on one H100, at best.

Signs: maths units sit idle, and speed follows memory speed.

R3Compute decides how fast the maths runs

Compute is maths operations per second. Reading a prompt uses each weight thousands of times, so compute sets the wait before the first word.

Example: a prompt of 4,096 tokens (word pieces) needs about 580 trillion operations for the weights alone.

Signs: maths units near full; long prompts slow; smaller number formats help a lot.

R4Communication cost decides how well many chips work as one

When work is split, chips must swap results. Slow links or very frequent swaps waste time.

Example: split over GPUs, Llama 3.3 70B swaps results 160 times per writing step.

Signs: adding GPUs gives less speed than expected.

R5The workload decides which limit matters

Model size, prompt length, reply length and number of users change which limit you hit first.

Example: one user hits bandwidth. Hundreds of users with short chats hit compute. Hundreds with long chats hit capacity.

Signs: the same hardware feels fast for one job and slow for another.

R6Fixing one limit exposes the next

Every fix moves the bottleneck. Faster memory makes maths the limit. More GPUs make talking the limit.

Example: sharing each weight read among many users fixes weight cost. Then each user's own chat notes and memory size take over.

Signs: a big upgrade gives a small gain.

Chapter a · Tier 1

The LLM in 5 minutes

R1CapacityR2BandwidthR5Workload
Gut feeling

An LLM (large language model: the AI inside a chatbot) is a giant calculator. It guesses the next word piece, again and again. Each guess uses all its billions of learned numbers, kept in chip memory in a data centre. Rule of thumb: answer speed depends on how fast those numbers reach the maths.

Layers idea → how it works → real numbers

L1The idea

Text goes in as tokens (word pieces, like “sky” or “ing”). Each token passes through a stack of layers (repeated processing steps; our example model has 80). Each layer uses weights (billions of learned numbers: the model's frozen “brain”). At the end, the model scores every possible next token and picks one. Then it repeats, one token at a time.

L2How it works

Inside each layer, two blocks take turns. Attention (the part that lets each token look back at earlier tokens) mixes in context. The FFN (feed-forward network: a big block of maths applied to each token on its own) transforms the result.

To look back, attention needs notes about every earlier token. Those notes are the KV cache (key-value cache: saved calculations about every earlier token in this chat). With it, the model does not redo old work for each new token.

The KV cache is not learned knowledge. It is not a permanent record of old chats either. It belongs to one conversation. Some systems keep it for a while, so a returning chat can reuse it.

L3Fine details and real numbers

Our running example is Llama 3.3 70B. Its public model card lists 80 layers and a hidden size of 8,192 numbers per token. Attention is split into heads (parallel look-back units): 64 query heads, but only 8 KV heads (heads that keep saved notes). Each head works with 128 numbers.

The model has about 70.6 billion weights. At 16 bits (2 bytes) each, they fill about 141 GB. At FP8 (8 bits, 1 byte each), about 70.6 GB. Its tokenizer knows 128,256 different tokens.

So two piles of data matter for hardware. The weights are the same for every user and never grow. The KV cache is separate for each user, and it grows with every token.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if the model had twice as many layers? The weights would roughly double. The KV cache per token would double too. Both hardware piles grow together.

Common wrong belief

“The model looks facts up in a database.” No. There is no lookup table. Knowledge is spread across billions of weights. In a dense model, every token touches all of them.

Surprising angle

Most of the cost of “thinking” is not the maths. It is moving the weights from memory to the maths units, again and again.

Trade-offs and open debates

Bigger models know more but need more memory and more time per token. Open debate: run one huge model, or a smaller model that thinks longer by writing more tokens?

Chapter b · Tier 1

The chip

R1CapacityR2BandwidthR3Compute
Gut feeling

A GPU (graphics processing unit: a chip with thousands of small maths units working at once) is a kitchen with thousands of cooks. An ordinary computer chip is a few master chefs. Rule of thumb: for mountains of the same simple maths, many cooks win. Data-centre servers hold four or eight GPUs each.

Layers idea → how it works → real numbers

L1The idea

A CPU (central processing unit: the general chip in every computer) is fast at many different tasks, one after another. A GPU trades that flexibility for width. It runs the same instruction on thousands of numbers at once. LLM (large language model) maths is mostly matrix multiplication (multiplying big grids of numbers), so width wins.

Building blocks first. A transistor (a tiny electric on-off switch) is the basic part. A die (one rectangle of silicon cut from a wafer) holds billions of them. Chiplets (several dies joined in one package) get around the size limit of a single die.

L2How it works

A GPU die holds many SMs (streaming multiprocessors: the GPU's mini-processors; an H100 has 132). Each SM holds Tensor Cores (circuits that multiply small grids of numbers in one go). Beside them sit registers (the tiniest, fastest storage, right at the maths units).

Each SM also has SRAM (static memory: very fast on-chip storage, used as shared memory and L1 cache). All SMs share an L2 cache (a bigger on-chip buffer: 50 MB on H100). Off the die sits HBM (high-bandwidth memory: very fast memory stacked right beside the chip, like a fridge next to the chef).

Packaging joins it all. The dies and HBM stacks sit on an interposer (a slab of silicon wiring with very fine lines). It carries thousands of wires between die and memory. B200 joins two dies with a 10 TB/s link, so software sees one GPU.

L3Fine details and real numbers

Number formats set how many bits each number uses. FP16 (16-bit floating point: 2 bytes per number) is the classic. FP8 (8 bits: 1 byte) halves memory and roughly doubles Tensor Core speed.

FP4 (4 bits: half a byte) halves both again. NVIDIA's NVFP4 (its FP4 version) adds one small scale factor per 16 numbers, so it averages 4.5 bits.

Speed is counted in TFLOPS (trillions of maths operations per second). Spec sheets often quote “with sparsity” numbers. Those assume half the weights (the model's learned numbers) are zero, and they double the figure. This guide uses the plain, dense numbers.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if you used only CPUs? Small models run fine; people run them on laptops. But a big server CPU's memory moves roughly 600 GB/s at best Estimate. An H100 moves 3,350 GB/s. For writing replies, that gap alone makes the GPU several times faster.

Common wrong belief

“GPUs are fast because their clock is faster.” No. GPU clocks run near 2 GHz, like CPU clocks. The speed comes from width: thousands of maths units on one big grid at once.

Surprising angle

For chatbots, the most important number on a GPU spec sheet is often not TFLOPS. It is memory bandwidth (data moved per second), in TB/s.

Trade-offs and open debates

A single die cannot exceed about 850 square millimetres, the limit of the chip-printing machine. So makers join dies together. The cost: die-to-die links use power and add delay. Open debate: one wafer-sized chip (Cerebras) or many normal chips (everyone else)?

Chapter c · Tier 1

The memory ladder

R1CapacityR2BandwidthR6Next limit
Gut feeling

Memory is a ladder. Each step down holds more, but it is slower and cheaper. The maths units sit at the top, hungry. Rule of thumb: the further data lives from the maths, the longer the trip. Most speed tricks keep the right data on the top steps.

Layers idea → how it works → real numbers

L1The idea

Picture a chef. The knife in hand is the registers (tiny storage right inside the maths units). The cutting board is SRAM (fast scratch memory on the chip). The fridge beside the chef is HBM (high-bandwidth memory: very fast memory stacked right beside the processor chip).

The pantry down the hall is CPU memory (memory attached to the CPU, the server's main processor). The warehouse across town is an SSD (flash storage, our “hard drive”).

L2How it works

Two numbers describe each step. Latency (how long one trip takes) and bandwidth (how much data arrives per second). For LLMs (large language models), bandwidth matters most, because we stream huge amounts. GPUs hide latency by keeping thousands of requests in flight, like a conveyor belt that is always full.

Why not make everything fast? SRAM uses six transistors (tiny switches) per bit. DRAM (the memory type inside HBM and CPU memory) uses one transistor and one tiny charge store per bit. So DRAM packs far more bits per chip, but each access is slower.

HBM's trick is width, not speed per wire. Each stack talks over 1,024 wires, and HBM4 doubles that to 2,048. A normal memory stick uses 64. The stacks sit millimetres from the die (the main slab of chip silicon).

L3Fine details and real numbers: the memory wall

Compute has grown much faster than memory bandwidth. Divide a chip's maths speed by its memory speed. You get operations per byte: how much reuse each byte needs to keep the maths busy.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if HBM were as slow as an SSD? Reading 70.6 GB of weights (the model's numbers) at 25 GB/s takes about 2.8 s. That means one token (word piece) every few seconds.

Common wrong belief

“More memory makes the model faster.” Size and speed are different. A bigger fridge does not open faster. HBM size decides what fits. HBM bandwidth decides speed.

Surprising angle

All the SRAM on an H100 holds well under 0.1% of a 70B model. Yet Groq and Cerebras build everything around SRAM. They use hundreds of chips, or a whole wafer, to get enough of it.

Trade-offs and open debates

HBM is expensive and its supply is tight. Makers trade more stacks (capacity and bandwidth) against cost, power and heat. Open debate: can memory keep up, or will compute keep running ahead?

Chapter d · Tier 1

Weights: the recipe book

R1CapacityR2BandwidthR4Communication
Gut feeling

The model's learned numbers are its recipe book. Rule of thumb: book size = numbers × bytes per number. So 70 billion numbers at 2 bytes fill 141 GB, but one AI chip holds about 80 GB. The book is split across chips. Before any answer, it must load: a cold start (the slow first load of a model).

Layers idea → how it works → real numbers

L1The idea

Weights (the model's learned numbers) are fixed. Every user shares the same copy. Their size is simple: number of weights × bytes per weight.

Llama 3.3 70B has about 70.6 billion weights. At 16 bits (2 bytes): about 141 GB. At FP8 (1 byte per number): 70.6 GB. At FP4 (about 0.56 bytes, counting scale factors): about 39.7 GB.

L2How it works

During serving, all weights sit in HBM (high-bandwidth memory beside the GPU die). They must, because every writing step reads them all. If they do not fit in one GPU, they are split across several. The GPUs then work as one over NVLink (NVIDIA's fast chip-to-chip link).

A cold start (loading a model onto empty GPUs) moves weights from storage into HBM. The path runs from network storage, through server memory, into HBM. At about 5 GB/s from network storage, 141 GB takes about 28 s. From local SSD (flash storage) at about 25 GB/s, about 5.6 s. Software start-up adds more Estimate.

L3Fine details and real numbers

Usable memory is less than the label. The software needs working space. This guide assumes 90% is usable Estimate.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if you shrink the numbers from 16 bits to FP4? Weights shrink about 3.5 times. You free memory for more users, and each step reads fewer bytes. The cost is some accuracy, which careful methods keep small.

Common wrong belief

“If it fits, it's fast.” Fitting is not speed. A model that only just fits leaves little room for the KV cache (saved chat notes), so few users fit.

Surprising angle

Weights are the easy pile. They are fixed in size and shared by everyone. The hard pile is the KV cache (saved chat notes), which grows with every user and every token (word piece).

Trade-offs and open debates

Keep spare “warm” GPUs with weights loaded? That is fast, but idle hardware costs money. Load on demand instead? That is cheap, but users wait through cold starts. Many services keep popular models warm and load rare ones on demand.

Chapter e · Tier 1

Reading vs writing: prefill and decode

Gut feeling

Answering needs two kinds of work. Reading your prompt is one big burst of maths, on every token (word piece) at once. Writing the reply is a slow loop: one token per step, and each step rereads all the model's learned numbers. Rule of thumb: reading waits on maths; writing waits on memory.

Layers idea → how it works → real numbers

L1The idea

The reading step is called prefill (processing the whole prompt in one go). The writing step is called decode (making one new token per step). Prefill runs all prompt tokens through the model together. Decode cannot: token 51 depends on token 50, so it must wait.

Two numbers measure them. TTFT (time to first token) is the pause before the first word; it is mostly prefill. Tokens per second is the typing speed after that; it is decode.

L2How it works

Each weight read from memory can feed many maths operations, or only a few. That ratio is arithmetic intensity (maths operations per byte moved).

In prefill, each weight is used once per prompt token: thousands of times. The maths units stay busy, so prefill is compute-bound (limited by maths speed).

In decode with one user, each weight is used once per step. The maths finishes at once, then waits for the next bytes. So decode is memory-bandwidth-bound (limited by how fast memory delivers data).

Every chip has a balance point: the operations per byte where maths and memory take equal time. For H100 in FP8 (8-bit numbers) it is about 590. Decode with FP8 weights (the model's numbers, 1 byte each) does about 2 operations per weight byte, per user. So roughly 300 users must share each read to reach balance.

L3Fine details and real numbers

Prefill of a 4,096-token prompt on Llama 3.3 70B needs about 580 trillion operations for the weights. Attention (the look-back part of each layer) adds more. On 4 H100s, the Lab's estimate is about 145 ms.

Decode for one user reads all 70.6 GB of FP8 weights per step. Even at full speed, one H100 needs 21 ms for that. That caps one user near 47 tokens per second, whatever the maths speed.

The balance shifts with the workload. More users push decode toward compute. Longer prompts make prefill heavier, because attention grows with the square of the length. They also make decode read more KV cache (saved chat notes).

Surprising angle

Trade-offs and open debates

Chapter f · Tier 1

The KV cache

R1CapacityR2BandwidthR5WorkloadR6Next limit
Gut feeling

The KV cache (saved notes about every earlier word piece in this chat) is the model's scratchpad. It saves repeated work, but it costs memory. It grows with every word piece and every user. Rule of thumb: with long chats and many users, the cache, not the model itself, fills the chip's memory.

Layers idea → how it works → real numbers

L1The idea: why it exists

For each new token (word piece), attention (the part that looks back at earlier tokens) compares it with every earlier token.

Each earlier token needs two lists of numbers per layer (processing step). The key (what this token offers for matching) and the value (what it passes on when matched).

Those lists never change once made. So we compute them once and save them. That saved set is the KV cache. It trades memory for time.

L2How it works: the size formula

KV bytes per token = 2 (key and value) × layers × KV heads × head size × bytes per number

KV heads are the groups of attention units that keep saved notes. Head size is how many numbers each head uses. For Llama 3.3 70B at 16-bit: 2 × 80 × 8 × 128 × 2 = 327,680 bytes. That is 320 KiB, about 0.33 MB, per token.

A 128K-token chat (131,072 tokens) holds about 40 GiB, which is about 43 GB. That is over half an H100, for one user.

Each user has their own cache, because keys and values describe one specific conversation. Two different chats share nothing. The exception is identical prompt beginnings, covered in chapter h.

Trade-offs and open debates

Keep the cache (memory) or recompute it (maths)? For a returning chat, recomputing a long prompt costs seconds of GPU (AI chip) time. Keeping it costs memory. Open debate: compress the cache and risk accuracy, or buy more memory?

Chapter g · Tier 2

Batching: one trip, many riders

R2BandwidthR3ComputeR5WorkloadR6Next limit
Gut feeling

Batching (serving many users in the same step) is like a bus. The trip, reading the whole model from memory, costs the same with 1 rider or 64. Rule of thumb: more riders, cheaper tickets. But every rider still carries a personal bag, and bags are never shared.

Layers idea → how it works → real numbers

L1The idea

A decode step (one writing step) reads all weights (the model's learned numbers) once. With 64 users in the batch, those bytes make 64 tokens (word pieces), not 1. So the weights' cost per token falls 64 times. That is why serving many people together is cheaper per token.

Continuous batching (users join and leave the batch at every step) keeps the bus full. Without it, everyone waits for the longest answer in the group to finish.

L2How it works: what does not get cheaper

Each user's bag is their KV cache (saved notes about every earlier token in their chat). It must be read in full at every step. So the bytes per step are the weights once, plus every user's cache.

As users grow, cache reads grow in a straight line. In the Lab's default setup, cache bytes pass weight bytes at about 50 users.

Maths grows with users too. Near the chip's balance point, compute becomes a limit. On H100 in FP8 (8-bit numbers), that is roughly 300 users, ignoring cache reads.

Chapter h · Tier 2

KV cache tiers: from fast shelf to basement

R1CapacityR2BandwidthR4CommunicationR6Next limit
Gut feeling

When the chip's fast memory fills, saved chat notes move down the memory ladder. Think of old files going to a basement. Active chats stay on top. Paused chats go to the server's main memory, then an SSD (flash storage), then shared storage. Rule of thumb: fetching saved notes beats recomputing them, if the link is fast enough.

Layers idea → how it works → real numbers

L1The idea

The saved notes are the KV cache (keys and values for every earlier token). Three ideas manage it. Paging (storing the cache in small fixed blocks, like pages in a notebook) stops memory being wasted.

Prefix reuse (prompts that start the same share one cache) avoids repeated work. Tiering (moving cold blocks to cheaper memory) frees the fast memory for active chats.

L2How it works

NVIDIA's Dynamo (open-source software that runs AI serving) names four tiers Official. G1 is GPU memory (HBM on the AI chip). G2 is CPU memory (the server's main memory). G3 is local SSD. G4 is shared network storage.

Moving between machines needs RDMA (remote direct memory access: one machine writes straight into another's memory without its CPU's help). NIXL (NVIDIA's data-moving library) moves cache blocks between GPUs, memory and storage.

Shrinking the cache helps every tier. Options: 8-bit or 4-bit cache, fewer KV heads (cache-keeping attention units), compressed notes, or dropping very old tokens.

Chapter i · Tier 2

Splitting a giant model across GPUs

R1CapacityR4CommunicationR6Next limit
Gut feeling

When the recipe book is too big for one kitchen, you split it. Each kitchen keeps part of the book and passes half-finished dishes to the others. Rule of thumb: splitting buys memory and speed, but every split adds talking between chips.

Layers idea → how it works → real numbers

L1The idea: four ways to split

  • By layers. Pipeline parallel (each GPU runs a group of layers, the model's processing steps, like stations on an assembly line).
  • By slices. Tensor parallel (every GPU holds a slice of every layer, and they combine results each layer).
  • By experts. Expert parallel (each GPU holds some “experts” of an MoE model). MoE means Mixture-of-Experts: a model of many small blocks, where each token (word piece) uses only a few.
  • By copies. Data parallel (whole copies of the model serve different users).

L2How it works: the price of talking

Tensor parallel needs two all-reduces (a group step where every GPU shares its part and all end with the sum) per layer. With 80 layers, that is 160 per decode step (writing step). Each is small, but each waits for the slowest GPU. So tensor parallel wants the fastest links: NVLink (NVIDIA's chip-to-chip link) inside one group.

Pipeline parallel talks less: once per stage boundary. But it creates bubbles, where GPUs wait for each other, unless many requests are in flight.

Expert parallel uses all-to-all traffic (every GPU sends to every other) twice per MoE layer. Tokens go out to their experts, then results come back.

L3Fine details and real numbers

Llama 3.1 405B at FP8 (1 byte per number) is 406 GB. On 8 H200s (1,128 GB), over half the memory is left for cache.

DeepSeek-V3 has 671 billion weights (learned numbers), but each token uses only about 37.5 billion. Each MoE layer has 256 experts, and each token picks 8. With one user, decode reads only the chosen experts. With 64 users, tokens touch about 222 of 256 experts per layer. So big batches read most weights anyway.

An NVL72 rack (one frame of 72 GPUs) makes them one NVLink group. In total it moves 130 TB/s on GB300. On Vera Rubin, NVIDIA's current page lists 216 TB/s Official. That suits expert parallel for big MoE models.

What if

Common wrong belief

“Twice the GPUs, twice the speed.” Not quite. Each split adds talking. Past a point, adding GPUs adds more talking than speed.

Surprising angle

MoE models are “big but cheap” mainly at small batches. At large batches, nearly every expert gets used, so you read nearly all weights. The saving moves from bandwidth to maths: each token still does only about 37.5 billion weights' worth of maths.

Trade-offs and open debates

Tensor parallel: low delay, heavy talking. Pipeline: light talking, bubbles. Expert parallel: scales MoE, but popular experts create hot spots. Open debate: wide expert parallel across a whole rack, or many smaller copies?

Chapter j · Tier 2

The wiring

R2BandwidthR4CommunicationR6Next limit
Gut feeling

Chips talk over roads of different sizes. Inside one server cabinet, NVLink (NVIDIA's chip-to-chip link) is a wide motorway. Between cabinets, the network is a busy city road. Rule of thumb: keep the chattiest work on the motorway.

Layers idea → how it works → real numbers

L1The idea

Scale-up (making many GPUs act as one machine) uses NVLink. NVLink Switch chips (traffic hubs for NVLink) let every GPU in the group reach every other at full speed.

Scale-out (joining many servers into one cluster) uses NICs (network interface cards).

NICs plug into switches running InfiniBand or Ethernet, the two main families of data-centre network.

Inside many servers, PCIe (the standard plug-in link inside computers) connects GPUs to CPUs (main processors), NICs and SSDs (flash drives).

L2How it works

RDMA (remote direct memory access) lets one machine write straight into another's memory. No CPU is in the way, so delays stay short. GPUDirect RDMA goes further: the NIC reads and writes GPU memory directly.

A DPU (data processing unit, such as NVIDIA BlueField) is a network card with its own CPU cores. It handles storage, security and network chores, so the main CPU and GPU need not.

Bandwidth is the road's width. Latency is the trip time for one car. A 1.3 GB cache transfer cares about width. A chain of 160 small exchanges cares about trip time.

Chapter k · Tier 2

The building

R1CapacityR4CommunicationR6Next limit
Gut feeling

An AI data centre is a factory that turns electricity into answers. Servers stack into racks (tall metal frames of computers). Rule of thumb: one modern AI rack draws as much power as 100 to 160 homes. Power and cooling, not chips, often decide how many racks you can run.

Layers idea → how it works → real numbers

L1The idea: four sizes

  • Tray. One flat server board. In an NVL72 (a 72-GPU rack) it holds 4 GPUs (AI chips) and 2 CPUs (main processors).
  • Rack. A tall frame of trays, switches and power units. An NVL72 has 18 compute trays and 9 switch trays for NVLink (the fast GPU-to-GPU link).
  • Pod. A group of racks joined by scale-out networking (the network between racks). NVIDIA's Vera Rubin POD has 40 racks Official.
  • Data centre. The building: power feed, cooling plant and many pods.

L2How it works: power and cooling

A GB200 NVL72 rack draws about 125–135 kW Official. A Vera Rubin NVL72 can pass 200 kW Reported. An average US home used 10,791 kWh in 2022: about 1.2 kW on average Official. So one rack equals roughly 100 to 160 homes.

Air cannot carry that much heat. Cold plates (metal blocks with water channels) sit on each chip. A CDU (coolant distribution unit) pumps liquid through the rack. Vera Rubin trays have no fans. NVIDIA says water at up to 45 °C can cool them without chillers Reported.

L3Fine details: tokens per watt

The useful score is tokens (word pieces) per second per watt, or its inverse: energy per token. Energy per token = power ÷ tokens per second.

With your current Lab settings, the estimate is about 1.9 J per token. That counts the servers' full power, not the building's cooling Estimate.

Batching (serving many users per step) improves tokens per watt. Idle GPUs ruin it, because they still draw power.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if your building has 10 MW of power? At 200 kW per rack, that is 50 racks before cooling and losses. Count those, and it is nearer 40 Estimate. Power, not money for chips, can set your size.

Common wrong belief

“Data centres are rooms full of noisy fans.” The newest AI racks are mostly liquid-cooled. Vera Rubin trays have no fans at all.

Surprising angle

Warm water cools well. Chips run above 80 °C, so 45 °C water still pulls heat away. The warm water that returns can even heat nearby buildings.

Trade-offs and open debates

Denser racks keep NVLink cables short. But they need liquid cooling and new power systems, such as 800-volt DC. Open debate: build huge single sites with cheap power, or spread out to ease strain on the grid?

Chapter l · Tier 2

Splitting the work: disaggregated serving

R4CommunicationR5WorkloadR6Next limit
Gut feeling

Disaggregated serving (separate machines for reading prompts and writing replies) is a restaurant with a prep kitchen and a plating line. Each is tuned for its job. But every order's notes must be carried across. Rule of thumb: split when long prompts keep interrupting typing, and the carry is cheap.

Layers idea → how it works → real numbers

L1The idea

In one shared pool, a long prefill (reading a prompt) blocks decode (writing replies) for everyone on those GPUs (AI chips). Users see the typing pause. Splitting gives prefill its own pool and decode its own pool. Decode never waits for prefill again. You can tune first-word time and typing speed separately.

L2How it works: the costs

Transfer. The prompt's KV cache (saved notes for each prompt token) must move to the decode pool. Its size is prompt tokens × bytes per token. Sent one layer (processing step) at a time over RDMA (direct memory-to-memory network transfer), much of it hides behind prefill.

Idle machines. If the mix of work changes, one pool can sit idle while the other is swamped. Pool sizes must be tuned and retuned.

The same-pool fix. Chunked prefill cuts long prompts into small chunks mixed into decode steps. It limits stalls without moving data. The docs of vLLM (a popular open-source serving engine) call split pools experimental. They say split pools do not raise throughput Official.

L3Fine details: three real splits, and a dated case study

NVIDIA's Groq 3 LPX racks (racks of special decode chips) pair with Vera Rubin GPUs Official. LPX chips keep weights (the model's numbers) in SRAM (very fast on-chip memory).

Each server board in an LPX rack also has DRAM (ordinary, slower memory). NVIDIA documents three ways to split:

  • Attention–FFN split. Rubin GPUs do prefill and decode attention (the look-back part), where the big cache lives. LPX runs the FFN (the feed-forward block of each layer) and expert layers. Small activations cross at every layer, every token. Lesson: decode's two halves hit different limits.
  • Whole decode. Rubin does prefill and hands the cache to LPX once per turn. LPX does all of decode. Lesson: decode is bandwidth-bound (limited by memory speed), so run it where bandwidth is highest.
  • Draft model. A small model on LPX guesses tokens fast. Rubin checks them in one pass. Lesson: decode's real problem is one token per weight read.

A dated case study: Rubin CPX

NVIDIA announced Rubin CPX on 9 Sept 2025 for the “context phase”, its name for prefill. It had 128 GB of GDDR7 (cheaper graphics memory) Official. In March 2026, NVIDIA's Ian Buck said CPX was pulled from 2026 plans to focus on LPX Reported. In Sept 2026, analyst Ming-Chi Kuo said it may return in 2027 Unconfirmed.

Stress-test what-if · wrong belief · contrarian · trade-offs
What if

What if prompts are short and replies long? Prefill is tiny and stalls are rare. Splitting adds transfer and idle risk for little gain. The same pool wins.

Common wrong belief

“Disaggregation makes everything faster.” vLLM's own docs say it does not improve throughput. Its job is control over delays.

Surprising angle

The best split may sit inside decode, not between prefill and decode. NVIDIA's attention–FFN design cuts decode itself in two.

Trade-offs and open debates

More specialised pools tune better, but they create more ways to sit idle and more data to move. Open debate: will mainstream systems settle on split pools, or will smarter scheduling in one pool be enough?

Built on the Six Relationships

Cheat sheet

R1 · Capacity decides what fits

fits if (weights + all users' KV cache) ÷ GPUs ≤ 90% of memory per GPU

Llama 3.3 70B weights: 141 GB at 16-bit, 70.6 GB at FP8, about 39.7 GB at FP4.

Fixes: more GPUs, fewer bits, cache tiers. Next limit: talking between GPUs, or bandwidth.

R2 · Bandwidth decides how fast data arrives

decode step ≥ bytes read ÷ memory bandwidth

70.6 GB ÷ 3.35 TB/s = 21 ms, so at most about 47 tokens per second for one user on one H100.

Fixes: batching (helps weights only), fewer bits, faster memory, SRAM chips. Next limit: compute, or cache reads.

R3 · Compute decides how fast the maths runs

prefill ≈ 2 × weights × prompt tokens operations (+ attention, which grows with length²)

Balance point = maths speed ÷ memory speed. H100 FP8: about 590 operations per byte. Rubin: about 910.

Fixes: FP8 or FP4, more GPUs, prefix caching, chunked prefill. Next limit: talking between GPUs.

R4 · Communication decides how well chips act as one

tensor parallel: 2 exchanges per layer per step (160 for Llama 3.3 70B)

Per GPU, each way, on H100-era hardware: NVLink 450 GB/s vs network 50 GB/s.

Fixes: keep chatty splits inside NVLink, bigger NVLink groups, overlap talking with maths. Next limit: bandwidth or compute.

R5 · The workload decides which limit matters

  • One user: bandwidth.
  • Many users, short chats: compute.
  • Many users, long chats: capacity.
  • Giant model across racks: communication.

R6 · Fixing one limit exposes the next

  • Batching → cache reads and capacity take over.
  • Faster memory → compute takes over.
  • More GPUs → talking takes over.
  • Split pools → transfer time and idle machines appear.
  • SRAM chips → capacity becomes tight.

Numbers worth remembering

  • One token of Llama 3.3 70B's cache: 320 KiB, about 0.33 MB, at 16-bit.
  • One 128K-token chat: about 43 GB of cache.
  • H100: 80 GB at 3.35 TB/s. Rubin: 288 GB at 19.2 TB/s.
  • One modern AI rack draws as much power as 100 to 160 homes.
  • 8 bits make 1 byte, so 400 Gb/s = 50 GB/s.

Three questions for any AI chip

  1. How much fast memory does it have, and how fast is it? (R1, R2)
  2. How many operations per byte does it need to stay busy? (R3)
  3. How many can act as one, and over what links? (R4)

The big question, revisited

“One kind of chip starts the answer, another does the rest.” The verdict.

  1. Two kinds of work are real. Reading a 4,096-token prompt keeps the maths busy about 75% of the time. Writing replies for 32 users spends about 91% of each step moving data.
  2. One GPU type can do both. The Lab's default runs both on the same H100s, as most services still do. vLLM calls split pools experimental and says they do not raise throughput Official.
  3. Splitting is a design choice. In a shared pool, a new 4,096-token prompt stretches others' typing gap from 12 ms to 157 ms. Chunking cuts that to 30 ms. Splitting removes the gap. But moving the cache adds about 27 ms over one 400 Gb/s link. For a 128K-token prompt, it adds 859 ms.
  4. Real designs split in more than one way. NVIDIA's LPX can take all of decode, or only the FFN half of it, or run a draft model Official. Google plans separate training and inference TPUs Reported. A prefill-only chip, Rubin CPX, was pulled and may return Unconfirmed.

Verdict. Your hunch is a good first sketch and a wrong final picture. The split that always exists is in the work. Should different chips do the two kinds of work? That depends on the workload, the cost of moving the cache, and your goal. In late 2026, the boldest split is not even reading versus writing. It cuts the writing step itself in two.

For your current Lab settings: a new prompt would freeze typing for 145 ms. Moving its cache over 4 network links costs only 8.4 ms, so split pools (or chunked prefill) look worth it.
