Part 1

The mental model

First, the pictures you need in your head. You already know most of them from C.

1.1 · What you already know

Three kinds of things in every computer

A file on the disk

  • A file is bytes stored on the disk, with a name.
  • It does nothing by itself. It just sits there.
  • It stays when the power goes off.
  • Examples: hello.c, hello.exe. Soon: school.db.

A program running in memory

  • When you run a program, the computer copies its instructions into RAM. The CPU runs them, one by one.
  • A running program is called a process.
  • It can wait, work and answer.
  • When it stops, or the power goes off, its memory is wiped.
  • Example: your C program while it waits at scanf().

Two programs sending messages

  • One process cannot read another process's memory. The operating system keeps them apart.
  • So they talk by sending messages. A message is just bytes, often plain text.
  • Example: the browser sends the text GET /api/students/2/marks to our Python program.

Data that must last goes in a file. Work that must happen needs a running program. Two programs share data by sending messages.

1.2 · The problem

Why can't the web page just open school.db?

The school keeps every student's marks in one file: school.db. We want a web page that shows a student's marks.

Here is the simplest idea: the page opens school.db and reads the marks. Let's test that idea.

Can a web page open school.db by itself?

The answer is no. And even if it could, it should not. Here are four problems.

Problem 1

The page cannot reach the file

The page runs in the browser, on the user's device. That might be a phone at home. school.db is on the school's computer. A program cannot open a file on another computer's disk.

Even on one laptop, a page cannot open files on the disk by itself. The browser keeps every page in a sandbox. A page can only read a file that you pick by hand.

Problem 2

Everyone would see everything

To show one student's marks, the page would need the whole file. So every user would get every student's marks.

Problem 3

Anyone could change anything

The code in a browser belongs to the user. Press F12 and you can run your own JavaScript. So a rule written in the page, like "marks must be 0 to 100", can be skipped. A student could set his own Maths mark to 100.

Problem 4

The rules would be in a thousand places

If the rules lived in every user's page, then changing one rule means changing every copy. With one program in the middle, there is one place to change.

So we need a program in the middle

  • It runs on the school's computer, next to school.db.
  • Every browser sends its requests to it.
  • It checks the rules. Users cannot change its code.
  • It reads or changes only the data that is needed.
  • It sends back only what that user should see.

This middle program is the application tier. We will write it in Python, with a library called Flask. It is the "?" box at the top of this page.

Real apps also check who is asking, with a login. Our small app skips logins, so we can focus on the tiers.

Code in the browser belongs to the user. Code on the server belongs to the school. So the browser may only ask. Python decides, and only Python opens school.db.

1.4 · How they talk

Each tier talks only to its neighbour

Between Tier 1 and Tier 2: messages. They follow rules called HTTP. The data inside is JSON, which is just text.

Between Tier 2 and Tier 3: an SQL command goes in. Rows come out.

Tier 1 and Tier 3 never talk. That is the whole point of the middle tier.

One true detail: SQLite is a library, not a separate program. Its code runs inside the Python program. So Tier 2 talks to Tier 3 by calling SQLite's functions. Bigger databases, like PostgreSQL or MySQL, run as their own program. There, the SQL travels as messages. Either way, Tier 2 asks in SQL.

1.5 · Flask, explained with C

Flask is new to you. So let's build it from C.

We use only eight small parts of Flask. Each one maps to something you already know.

A server is a program that waits

Run this C program. It stops at scanf() and waits. It is not stuck. It is waiting for input. When input comes, it answers, then waits again.

A Flask server does the same thing. Its input comes from browsers: wait for a request → handle it → send an answer → wait again.

That is why, after you type python app.py, the terminal seems to freeze. It is waiting. Stop it with Ctrl+C, just like your C program. The last line of app.py, app.run(), starts this waiting loop.

Real Flask can work on a few requests at the same time. The idea is the same.

Routes are a table of function pointers

Flask keeps a table. Each row links a method and a path to one function. In C, you could build it with an array of structs that hold function pointers.

In Python, each line that starts with @app.get or @app.post adds one row to Flask's table. Such a line is called a decorator. When a request arrives, Flask finds the matching row and calls that function.

<int:roll> works like %d in sscanf(). Flask cuts the number out of the path and gives it to your function as an int. If there is no number there, no row matches, and Flask answers 404 NOT FOUND.

JSON is just text

The line this program prints is JSON. JSON is a standard way to write data as text, so every language can read it: Python, JavaScript, C.

In Flask, jsonify() turns Python data into JSON text. In JavaScript, res.json() turns JSON text back into objects.

SQLite is a C library

SQLite is written in C. Python's sqlite3 module is a thin layer on top of it. When our code runs a query, these real C functions run underneath.

This C program asks school.db for Meera's marks. It is what Python does for us in steps ④ to ⑥. We compiled it and ran it.

$ gcc marks.c -lsqlite3 -o marks $ ./marks Maths 92 Science 88 English 95

To compile it you need the SQLite library for C. You do not need it for the project. Python already has SQLite inside.

The ? in our SQL

Never glue what a user typed into SQL text. Write a ? instead, and give the value separately. SQLite puts the value in place of the ? as plain data, never as SQL commands. In C, that is sqlite3_bind_int64().

This stops a trick called SQL injection, where someone types SQL commands into an input box.

Every Flask part we use

  1. Flask(__name__) makes the app.
  2. @app.get(…) adds a GET row to the route table.
  3. @app.post(…) adds a POST row.
  4. <int:roll> cuts a number out of the path.
  5. request.get_json() reads the JSON the browser sent, as a dict.
  6. jsonify(…) turns Python data into a JSON response.
  7. app.send_static_file(…) sends a file from static/.
  8. app.run() starts the waiting loop.

Who does what

Flask does: waits for requests, reads the HTTP text, finds the right function, calls it, turns your return value into an HTTP response, and sends it back.

You write: the functions. They hold the rules, the SQL, and what to send back.

1.6 · A tier is a job, not a computer

Today: one laptop. In a real school: maybe three computers.

On your laptop, all three tiers run on one computer. The browser and Python are two processes. school.db is a file on the same disk.

In a real school, they could be far apart. Pages run on phones and laptops at home. Python runs on the school's server computer. The data lives on a database computer.

The jobs stay the same. The messages stay the same. Only the distance changes. That is why we say 3-tier is a logical split: a split of jobs, not of machines.

In a big school, Tier 3 would usually be a database server program, like PostgreSQL, on its own computer, instead of one SQLite file. The SQL questions look almost the same.

Where a file sits is not where it runs.

The files in static/ sit on the school's computer. But they run in the user's browser. Flask sends a copy of each one when the page opens. After that, the page runs on its own, and only asks Flask for data.

You can see this in the terminal when you open the page. These lines are from our test:

127.0.0.1 - - [21/Oct/2026 14:05:46] "GET / HTTP/1.1" 200 - 127.0.0.1 - - [21/Oct/2026 14:05:46] "GET /static/style.css HTTP/1.1" 200 - 127.0.0.1 - - [21/Oct/2026 14:05:46] "GET /static/app.js HTTP/1.1" 200 -

Three requests: the page, its looks, its actions. Then nothing, until you click a button.

  • Your browser may also ask for /favicon.ico, the small tab icon. We have none, so Flask answers 404 for it. That is fine.
  • Next time you open the page, you may see 304 instead of 200. It means "not changed: use the copy you already have".
  • After the first run, a folder named __pycache__ appears. Python keeps compiled copies of db.py and rules.py there, to start faster next time. A bit like the .o files a C compiler makes. You can ignore it.

Why the name static? Static means "sent exactly as it is". Flask sends files from a folder named static at addresses that start with /static/.

Why three Python files for one tier? One tier can have many files. app.py talks to browsers. rules.py holds the rules. db.py talks to the database. All three run inside one Python program, like several .c files compiled into one program. import lets one file use functions from another.

4.1 · Run it

Run it in five steps

  1. Install Python 3 from python.org. In the installer, tick Add python.exe to PATH. The python program reads .py files and runs them.
  2. Make a folder named school-app. Put the files in it, exactly like the tree in Part 3. index.html, style.css and app.js go in a folder named static. (All 8 files are also in school-app.zip.)
  3. Open a terminal in that folder. Open the folder in File Explorer. Click the address bar, type cmd, and press Enter. Open the Terminal app. Type cd and a space, drag the folder into the window, and press Enter. Right-click inside the folder and choose Open in Terminal.
  4. Type these three commands, one at a time:
    py -m pip install flaskdownloads Flask (only the first time). pip is Python's installer.
    py setup_db.pybuilds school.db and prints Created school.db with 3 students and their marks.
    py app.pystarts the server. It keeps running and waits.

Changed app.py, rules.py or db.py? Stop the server with Ctrl+C, then start it again. Python read those files when it started. The running program is a copy in memory. It does not see your new file.

3Tier 3 the SQLite engine and the file on the disk

What happens

Part 6

Break it on purpose

Engineers learn a system by breaking it carefully. For each experiment: write your guess, run it, then find the step where the journey stopped. Run it on your laptop, or in the lab below, or both.

Experiment 1

Stop the Python server

What still works when Tier 2 is gone?

On your laptop

  1. app.py is running and the page is open. Click Show Marks once. It works.
  2. Click on the terminal window. Press Ctrl+C. Flask stops.
  3. Do not refresh the page. Click Show Marks again.
  4. Now refresh the page.
  5. Start the server again with py app.py. Refresh. Click Show Marks.

At step 3, what happens?

What really happens

  • Step 3: the page stays on the screen. The box says Cannot reach the server. Is app.py running? The terminal shows nothing new. If DevTools is open, the Console shows a red line: Failed to load resource: net::ERR_CONNECTION_REFUSED.
  • Step 4: the browser shows its own error page, like This site can't be reached. The words depend on your browser.
  • Step 5: everything works again. Every mark is still there.

Why

The page is Tier 1. It was already in the browser's memory, so it stayed. Your click ran ① and tried ②, but no program was waiting for the message, so fetch() failed. Steps ③ to ⑧ never happened. Our app.js caught the failure and wrote the message, which is why ⑨ still shows something.

Refreshing failed too, because Flask also hands out the page files. And school.db was never touched. When Flask started again, every mark was still there, because marks live in a file, not in the program.

Experiment 2

Hide the database file

What happens when Tier 3's file is gone?

On your laptop

  1. Keep app.py running. Open the school-app folder.
  2. Rename school.db to school_old.db.
  3. Click Show Marks.
  4. Look at the folder again. Then look at the terminal.
  5. Undo: delete the new school.db, and rename school_old.db back to school.db. Click Show Marks.

At step 3, what happens?

What really happens

  • The box says Error 500 from the server. Look at the terminal.
  • The terminal shows a long error report, called a traceback. Here are its most useful lines:
[2026-10-21 14:05:50,610] ERROR in app: Exception on /api/students/2/marks [GET] Traceback (most recent call last): … 4 steps inside Flask … File ".../school-app/app.py", line 21, in get_marks rows = run_sql("SELECT subject, mark FROM marks WHERE roll = ?", (roll,)) # ④ ask Tier 3 File ".../school-app/db.py", line 10, in run_sql cur = con.execute(sql, args) # ⑤ SQLite runs the SQL on school.db sqlite3.OperationalError: no such table: marks 127.0.0.1 - - [21/Oct/2026 14:05:50] "GET /api/students/2/marks HTTP/1.1" 500 -
  • Surprise: a new file named school.db is in the folder. Its size is 0 bytes.

Why

db.py ran sqlite3.connect(DB). The file was missing, so SQLite made a new, empty school.db. That is what connect does: it opens a file, or creates it if it is not there.

Then the SQL asked for the marks table. The new file has no tables, so SQLite raised an exception at step ⑤. Nothing caught it, so Flask answered 500 INTERNAL SERVER ERROR.

Flask did not send the details to the browser, because error details can hold secrets. It printed them in the terminal, for you, the developer. Look at the traceback: it shows the line marked ④ and the line marked ⑤. You can see exactly where the journey broke.

The program was fine. The page was fine. Without the file, there is no data. That is why real schools keep backups of Tier 3.

Experiment 3

Ask for a student who does not exist

Is "nothing found" an error?

On your laptop

  1. Type 99 in the roll box.
  2. Click Show Marks.
  3. Click Show Details.
  4. Bonus: try -1. Is the message different?

At step 2, what happens?

What really happens

  • Show Marks: No marks for roll 99
  • Show Details: No student with roll 99
  • The terminal: "GET /api/students/99/marks HTTP/1.1" 404 -
  • With -1: Error 404 from the server. Look at the terminal.

Why

All nine steps ran. At step ⑥, SQLite returned an empty list: []. For SQLite, finding zero rows is a normal answer, not an error.

Tier 2 decided what an empty answer means: "not found". It sent status 404 with a JSON message, and Tier 1 showed it. Every tier did its job.

With -1, the path /api/students/-1/marks does not match <int:roll>, which takes no minus sign. So no route matches, and Flask itself answers 404 with an HTML page, not JSON. Our app.js sees that the answer is not JSON and shows its general error.

Experiment 4

Change a mark behind Tier 2's back

Does the page keep an old copy? Do the rules protect the file?

On your laptop

  1. Keep app.py running. Show the marks for roll 2. Maths is 92.
  2. Open a second terminal in the same folder.
  3. Type py change_mark.py 2 Maths 35. It prints Rows changed: 1.
  4. Go back to the browser. Refresh the page. Click Show Marks.
  5. Now type py change_mark.py 2 Maths 150. Refresh and click again.
  6. Put it back: py change_mark.py 2 Maths 92.

Type the subject exactly: Maths, Science or English. With maths, it prints Rows changed: 0, because SQL compares text exactly.

At step 4, what does the page show for Maths?

After the refresh, the box goes back to Type a roll number, then click a button. The old answer lived only in the browser's memory. Click Show Marks and you see Maths: 35. No restart is needed.

Why: nobody keeps a copy of the marks. Every click runs ② to ⑨ again, and step ⑤ reads school.db fresh. The page always shows what is in the file right now.

At step 5, a mark of 150. What happens?

change_mark.py prints Rows changed: 1, and the page shows Maths: 150. The rule did not stop it.

Why: the 0 to 100 rule lives in rules.py, in Tier 2. change_mark.py did not go through Tier 2. It opened school.db itself, so the rule never ran.

Rules only protect data that comes through Tier 2. That is why, in a real school, only Tier 2 may reach Tier 3.

A designer can also add a safety check inside Tier 3, like CHECK (mark BETWEEN 0 AND 100) in the table. Then even a direct change would be refused.

    7.2 · From memory

    Five questions

    Answer in your own words, without looking back. Press Hide the rest of the page to make that easy. When you finish an answer, compare it with ours.

    1. Which tier would you change if marks above 100 should be rejected, and why not the others? (Pretend rules.py does not check marks yet.)

      Tier 2, in rules.py. Every request passes through Tier 2, on the school's computer, so its check cannot be skipped.

      Not Tier 1: the user controls the browser and can skip any check there, with F12 or by sending a request without the page. A Tier 1 check is still nice, because it is fast and friendly. But it is not safe.

      Not Tier 3: it stores what it is given and does not know the school's rules. A designer can add a CHECK in the table as a second safety net, but the rule and its clear message belong in Tier 2.

    2. You pressed Ctrl+C to stop app.py, but the page stayed on the screen. Why did the page stay? And why did Show Marks stop working?

      The page is Tier 1. It was already copied into the browser's memory, and it runs there, so it does not need Python to stay on the screen.

      But Show Marks needs data, and data comes only through Tier 2. With the Python program stopped, the request at step ② had no program to go to. fetch() failed, and steps ③ to ⑧ never happened.

    3. Give two reasons why the web page never opens school.db itself.

      It cannot. The file is on the school's computer. The page runs in the browser, on the user's device, inside a sandbox that cannot open disk files by itself.

      It must not. The user controls everything in the browser. If the page could open the file, any user could read every student's marks, change any mark, and skip every rule.

    4. Meera's Maths mark is 92. What form is it in, and where is it: (a) inside school.db, (b) right after fetchall(), (c) inside the HTTP response, (d) right after res.json()?

      (a) One byte, 5C, in the file on the disk.

      (b) The number 92 inside the tuple ('Maths', 92), in a list, in Python's memory.

      (c) The characters 9 and 2 in the JSON text {"mark":92,…}, in a message from Python to the browser.

      (d) The number 92 in the JavaScript object {mark: 92, subject: "Maths"}, in the browser's memory. At step ⑨ it becomes letters on the screen.

    5. A friend wants to make a phone app for the same school. Which tiers can he keep exactly as they are? Which one does he replace? Why does this work?

      He keeps Tier 2 and Tier 3: app.py, rules.py, db.py and school.db. He replaces only Tier 1: the phone app is a new presentation tier.

      It works because Tier 2 sends plain data as JSON, not a finished web page. Any program that can send HTTP requests and read JSON can use the same routes, and the same rules still protect the data.
